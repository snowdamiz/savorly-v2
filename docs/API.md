# API conventions

Base path: `/v1`. Request/response bodies are JSON, except multipart uploads and successful `204` deletions. Errors have `{ "error": "A readable message", "requestId": "…" }`; the request id is also the `X-Request-Id` response header and appears in the API's access log, so support can find a failed request. Compressible responses over 200 bytes are gzip- or brotli-encoded when the client accepts it (narration audio never is). Health is `GET /health`.

The browser authenticates with an HttpOnly session cookie and `credentials: include`. Native clients send `Authorization: Bearer <session-token>`. Tokens are returned by login, registration and Apple/Google sign-in only for requests without an Origin header; browser code never receives them. Cookie mutations must have an allowed Origin header. All private lists and mutations are scoped to the authenticated account.

Older app builds stay installed for months, so the API only ever adds fields and routes; new behaviour on an existing route is opt-in through a parameter.

Every route allows 300 requests a minute per visitor address ([deployment](DEPLOYMENT.md#1-database-and-api) explains how the address is found behind a proxy). Request bodies other than `GET`, `HEAD` and `OPTIONS` are capped at 128 KiB (`413`), except `POST /media` and the sous-chef's image upload.

## Usernames

A handle is 3–24 lowercase letters, digits, dots or underscores that starts and ends with a letter or digit, with no two dots in a row; a few names that would read as Savorly itself are reserved. New kitchens get one from their name (`alexrivera`, or `alexrivera42` when that's taken), and registration and a first Apple or Google sign-in answer `"created": true` so the app can offer to change it straight away.

`PATCH /me` takes an optional `handle` (a leading `@` and capitals are normalized). Left out or unchanged, the current handle stays, including older generated ones the rules above would reject. An invalid handle is `400`, a taken or reserved one `409`. `GET /handles/:handle` answers `{ "handle", "valid", "available" }` while someone types; their own handle counts as available.

## Kitchen setup

`GET /me` includes `onboarded`: `false` for a new kitchen until it finishes or skips its setup (photo, name and username, food preferences, cooks to follow, meeting the sous-chef), which the app shows on every platform and resumes after a restart. `POST /me/onboarded` marks it done and answers like `GET /me`. Kitchens from before the setup existed count as set up. A first Google sign-in starts the profile photo from the Google account's picture.

## Apple and Google sign-in

`POST /auth/nonce` takes no body and answers `{ "nonce" }`, single-use and valid for 10 minutes. The app hands it to Apple or Google and sends the resulting ID token to `POST /auth/oauth` as `{ "provider": "apple" | "google", "token", "code", "name" }`. `code` and `name` are optional: Apple's authorization code lets the server revoke Apple access when the account is deleted, and `name` names a new kitchen. Limits are per visitor address and per route: 60 nonces and 30 Apple/Google sign-ins per 15 minutes (see [accounts and security](#accounts-and-security) for the others). Past a limit is `429`.

Signed out, `/auth/oauth` starts a session like login (the cookie, plus `token` without an Origin header) and adds `"created": true` for a new kitchen. From a signed-in session it connects the provider to that kitchen instead and answers `{ "ok": true, "connected": "apple" | "google" }`. A provider the server isn't configured for is `503`; a token that fails verification, or a missing, used or expired nonce, is `401`. Connecting an identity that belongs to another kitchen is `409`, and so is a first Apple or Google sign-in whose email already has a kitchen (accounts are never merged by email). A new kitchen needs a verified provider email (`400`) and open sign-ups (`403`); a suspended account is also `403`.

`GET /me` lists connected `identities` and `hasPassword`. A kitchen without a password confirms `DELETE /me` with `{ "provider", "token" }` from a fresh sign-in (with a new nonce) instead of `password`. See [sign-in](SIGN-IN.md).

## Accounts and security

Sign-in routes have their own limits per visitor address: registration 20 an hour; login 20, password-reset requests 5, reset codes 10 and Apple/Google sign-ins 30 per 15 minutes. Login also allows 10 attempts per account per 15 minutes, answering `429` "Too many sign-in attempts…" whether or not the account exists; a successful login or a password reset clears it. A forgot-password request mails at most 5 codes an hour to one address and otherwise still answers `{ "ok": true }`.

When `TURNSTILE_SECRET_KEY` is set, `POST /auth/register` and `POST /auth/forgot` need a Cloudflare Turnstile `turnstileToken` in the body (`400` when missing or rejected, `503` when Cloudflare can't be reached); `/capabilities` reports the public `turnstileSiteKey` (`""` when the check is off). Turn it on only once the app versions people use send the token.

`GET /session` always answers `200` with `{ "user": <GET /me> | null }`, so a signed-out visitor causes no `401`s; apps use it at startup. Sessions last 30 days and slide: past half their life, any authenticated request extends them, and a cookie client gets the cookie again. `GET /me/sessions` lists the account's devices, this one first: `[{ "id", "createdAt", "lastUsedAt", "expiresAt", "userAgent", "client", "system", "current" }]`, where `client` is `Savorly` (the app) or a browser name and `system` names the device's system, each `""` when unknown. `DELETE /me/sessions/:id` signs one out (`204`, `404` for an unknown id) and `POST /me/sessions/revoke-others` signs out every other device (`{ "revoked": n }`).

`POST /me/password` takes `{ "currentPassword", "newPassword" }`, or `{ "newPassword", "provider", "token" }` with a fresh Apple or Google sign-in for a kitchen without a password, and answers like `GET /me`. The new password follows the registration rules (12–72 characters); other devices are signed out and pending reset codes cleared. A wrong password here, on the email routes below and on `DELETE /me`, is `403` rather than `401`, which apps treat as signed out.

`POST /me/email` takes `{ "email", "password" }` (or `{ "email", "provider", "token" }`), mails a six-digit code to the new address and answers `{ "ok": true, "email" }`; `POST /me/email/confirm` takes `{ "code" }` and answers like `GET /me` with the new, verified address. Registration mails a welcome with a 24-hour code: `POST /me/verify-email` takes `{ "code" }` and `POST /me/verify-email/resend` sends another. `GET /me` reports `emailVerified`. Codes last 15 minutes (24 hours for the welcome) and allow 5 tries; a wrong or expired code is `400`, a taken address `409`, a server without email `503`, and a failed delivery `502`. These routes work exactly when `/capabilities` reports `passwordRecovery`. With email configured, the account also gets a note when its password or email changes (to the old address), when a new device signs in, and when it is deleted.

`GET /me/export` downloads everything the account holds as JSON (`Content-Disposition: attachment`): `profile`, `preferences`, `plan`, `connectedProviders`, `recipes` (drafts included, with their `equipment`), `reviews`, `cookbooks`, `saves`, `following`, `mealPlans`, `groceries`, `pantry`, `studioConversations[].messages` and `aiJobs`, then `cookSessions` (each with its `stepEvents`), `cookQuestions`, `connectedApps` ([assistants](#assistants)), `recipeEdits` and `kitchenNotes` ([your version](YOUR-VERSION.md)), `recipeSuggestions`, `creatorEarnings`, `creatorPayouts` and `payoutAccount` ([creator fund](#cook-sessions-and-the-creator-fund), [cook-tested recipes](#cook-tested-recipes)), and `imports` ([bulk imports](#bulk-imports): each batch's `purpose`, `site`, times, `links` and pasted `texts` with what became of them, and the `permission` a creator gave to import their own site), and `recordings`, each [family recording](#family-recipes) with the address of its audio and its transcript (`cookbooks` say whether each is shared with the `household`); never password hashes, provider tokens or billing ids (Stripe customer, subscription, account or transfer ids). A native app, which can't add its bearer token to a browser download, calls `POST /me/export-link` for `{ "url": "/v1/export/<token>", "expiresAt" }` and opens the API's base URL plus `url`; the link works once, for 10 minutes.

`GET /me/export/files` (5 an hour per member) downloads the same as files, one ZIP (`application/zip`, `Cache-Control: no-store, no-transform`) written while it downloads: `savorly-export.json`, a folder for each recipe (`recipe.md`, `recipe.json` and its photos, video, step photos and clips copied from the member's storage), `cookbooks.md`, CSV files of the lists, the "I cooked this" photos, the profile photo, and `README.txt`, which lists every file not included with its address ([switching](SWITCHING.md#the-export-as-files)). `POST /me/export-link` with `{ "format": "files" }` makes a link to it instead (`"json"`, the default, keeps the JSON file; anything else is `400`), and the link's `HEAD` says which. One archive downloads per member at a time: another is `429` and leaves a link unspent; past four at once on one API process it's `503`.

`POST /client-errors` (no session needed, 30 a minute per visitor, up to 16 KB) takes `{ "message", "stack", "componentStack", "platform", "appVersion", "url", "release" }` from the app's error handlers, writes one line to the API's log and answers `204`.

## Discovery

`GET /recipes?q=lemon&category=Italian&tag=Vegetarian&maxMinutes=30&sort=Quickest&limit=24&offset=0`

Parameters are optional. `limit` is bounded to 60; pagination uses `offset`. The supported sort labels are `For you` (newest), `Quickest`, and `Top rated`. Public search never returns drafts. Recipe detail returns a draft only to its author.

`q` matches each word as a prefix of words in the title, cuisine, tags, ingredient names and description, in any language and ignoring accents ("creme brulee" finds "Crème brûlée"), with English stemming on top, and tolerates typos in titles and ingredient names ("ricota"). Results are ranked by relevance; with `Quickest` or `Top rated`, the closest matches still come first. `Top rated` orders by a weighted rating, `(sum of ratings + 5 × site average) / (reviews + 5)`, so one five-star review doesn't outrank many good ones; recipes still show their plain average and `reviewCount`. `category` matches a cuisine ignoring case. `following=true` limits the list to cooks the account follows (`401` without a session). `fits=me` leaves out recipes with anything the signed-in member avoids ([allergens and diets](#allergens-diets-and-the-pantry)); for a guest it changes nothing. `cookTested=true` keeps only [cook-tested](#cook-tested-recipes) recipes. `GET /creators` takes `limit` (up to 100) and `offset`.

`GET /feed?limit=12` (1–24) builds the home screen in one request: `{ "hero": Recipe | null, "trending": [...], "quick": [...], "following": [...], "newest": [...], "cookAlong" }`. Trending is the most saved in the last 7 days (a cook-tested recipe counts as if it had half as many saves again, and at least two more), quick is 30 minutes or less, and following is empty for guests; the hero isn't repeated, but a recipe can be both trending and quick. `cookAlong` is this week's [cook-along](CREATOR-FUND.md#the-weekly-cook-along), `{ "week", "recipe", "cooks", "started" }` (the week's Monday in UTC, the recipe, its verified cooks this week, and how many members started cooking it this week), or `null` while the week has no public recipe; the shelves can repeat its recipe, which the app shows once. `GET /sitemap` lists `{ "recipes": [{ "id", "updatedAt" }], "creators": [{ "id", "handle", "updatedAt" }] }` for the Worker's sitemap, cached for an hour.

## Recipe shape

The shared Expo contract lives in `apps/mobile/src/lib/types.ts`; server validation is in `services/api/internal/app/models.go`.

```json
{
  "title": "Lemon toast",
  "description": "A simple little plate for a slow morning.",
  "cuisine": "American",
  "minutes": 10,
  "servings": 2,
  "difficulty": "Easy",
  "image": "",
  "video": "",
  "ingredients": [{ "name": "Sourdough", "amount": 2, "unit": "slices", "category": "Bakery" }],
  "steps": [{ "title": "Toast", "text": "Toast until golden and finish with your favorite toppings.", "seconds": 120 }],
  "equipment": ["Toaster"],
  "tags": ["Vegetarian", "Breakfast"],
  "calories": 0,
  "aiGenerated": false,
  "published": true
}
```

Recipes the API returns also carry `allergens`, the recipe's allergen and diet groups, and `ingredientFood`, one entry per ingredient in order: `{ "key", "allergens", "terms" }` ([allergens and diets](#allergens-diets-and-the-pantry)). Both are read from the ingredients when a recipe is saved; anything sent in them is ignored.

Each step may also carry `timing`, how it spends its time for the [meal timeline](#meal-timeline): `{ "active", "wait", "oven", "burners", "estimated" }`, seconds that need the cook's hands and seconds that need no attention (each 0–86,400), the oven's heat in °C while it runs (0 for none, else 50–300), the burners it takes (0–6), and `estimated` when a model or a reading of its words guessed them; any of them may be left out as 0 (`400` otherwise). A step with only an oven heat preheats it. Leaving `timing` out on an update, as older apps and the sous-chef do, keeps the saved timing of the step with the same text; `null` clears it, and the server estimates the step instead. Imports fill in what a page's steps say as estimates, and recipe jobs and the sous-chef's drafts ask the model for it.

`equipment` is optional: what the recipe needs besides its ingredients (pots, pans, appliances, tools), as its author names them and in their order, up to 20 names of 1–60 characters (`400` otherwise); names are trimmed and blank or repeated ones (ignoring case) dropped. Leaving it out on an update, as older apps and the sous-chef's drafts do, keeps the saved list; `[]` clears it. Recipes the API returns always carry `equipment` (`[]` for none), `equipmentDetected`, the equipment the method mentions, and `equipmentGuess`, what it likely uses and when ([equipment](#equipment)), which is read from the steps when a recipe is saved; anything sent in it is ignored.

`language` is optional: one of `en`, `fr`, `de`, `ru`, `es`, `it`, `pt`, `zh`, `ja` or empty (regional tags such as `pt-BR` are shortened), and leaving it out on an update keeps the saved one. Cuisines on the app's list are stored with its spelling ("italian" becomes "Italian"); others are trimmed and capitalized. Names, units, tags and step text are trimmed, and empty or repeated tags dropped.

Media is optional. Use the URL returned by an [upload](#uploads), or in production a URL on a host listed in `MEDIA_HOSTS`; profile photos may also be a Google account picture. Media a recipe already has stays allowed when it is edited. The local development API accepts any HTTPS URL and localhost HTTP media. Ingredients and steps remain required even when a video is attached so the recipe can be searched, scaled, planned, and cooked accessibly. Each step may also carry a photo and a short clip ([step media](#uploads)). The app no longer shows or sets a recipe's own `video`, since clips belong to steps now; the field stays for released apps, and the app sends a saved one back as it is.

## Cookbooks, kitchen and groceries

`GET /library?limit=24` returns at most that many recipes (the most recently saved or written first) with `"hasMore"`; the ids, saves, cookbooks and follows stay complete, and without `limit` every recipe comes as before. Either way it also has `ownIds`, every recipe the member wrote (drafts too, newest first), and `publishedCount`, how many of them are published. The app asks for the newest 24 and pages through the rest. `GET /library/recipes?scope=saved|mine&collection=<id>&offset=0&limit=24` pages through saved or the account's own recipes as `{ "recipes", "hasMore" }`. `GET /kitchen?from=2026-10-12&to=2026-11-08` limits meal plans to that range of up to 62 days (`400` otherwise); groceries and pantry are always complete.

Grocery amounts are written with at most two decimals, and cups and spoons as fractions (⅓ cup). `POST /planner` and `POST /recipes/:id/groceries` take a published recipe or one of the account's own, published or not (`404` for anyone else's draft): plans are the account's alone, and a list only gets the ingredients. Adding a recipe's ingredients, or a week's with `POST /planner/groceries { "from", "to" }` (every planned meal in the range, scaled to its servings), merges each into an unchecked line with the same name and unit; both answer `{ "added", "merged" }`. `DELETE /recipes/:id/review` deletes the account's own review (`404` when there is none); an edited review keeps its `createdAt` and gets a new `updatedAt`. A recipe's author can answer each review on it: `PUT /recipes/:id/reviews/:review/reply` takes `{ "body" }` (2–1,000 characters) and answers `{ "reply": { "body", "repliedAt" } }`, sending again changes the answer, and `DELETE` on the same path removes it (`404` for anyone else, or when there is no answer). Reviews carry `reply`, the answer or `null`, and a new answer (not an edit) sends the reviewer a push notification under their comments setting.

## Allergens, diets and the pantry

The API reads every ingredient line with an ingredient lexicon (`services/api/internal/app/food.go` and `food_lexicon.go`): about 280 common ingredients with their names in the app's nine languages, what each is a kind of (cheddar is a cheese), what it is made from (soy sauce has soy and wheat), and its groups. The groups are the EU's fourteen allergens (`milk`, `egg`, `fish`, `shellfish`, `mollusc`, `treenut`, `peanut`, `gluten`, `soy`, `sesame`, `celery`, `mustard`, `lupin`, `sulphite`) and what diets leave out (`meat`, `pork`, `poultry`, `alcohol`, `gelatin`, `honey`). Longer names win, so peanut butter is never butter and nutmeg never a nut; "gluten-free", "sans gluten", "vegan" and the like cancel what they name; German compounds are read by their parts. A name the lexicon doesn't know keeps its own words. Each line's `key` names what it is, `allergens` its groups, and `terms` what an avoid list's own words are matched against. None of this knows what a packet holds or about cross-contact, and the app says so wherever it warns.

`GET /me` answers `avoid`, read from the member's diets and allergies whenever `PATCH /me` changes them: `{ "groups": { "peanut": ["Peanuts"], "meat": ["Vegetarian"] }, "terms": { "kiwi": ["kiwi"] } }`, each with what the member wrote that leads to it. Diets map to groups (vegetarian, vegan, pescatarian, gluten free, dairy free, nut free, halal); an allergy is a group in any of the nine languages ("lactose", "Erdnüsse", "花生过敏"), an ingredient ("cilantro", which also avoids coriander and 香菜), or else its own words. The sous-chef's recipe search uses `fits=me` unless the member asks for a recipe regardless.

`GET /kitchen` also answers `pantryCover`, every ingredient key the pantry covers (an item covers its key and what it is a kind of). `GET /kitchen/pantry-recipes?limit=12` (up to 24) answers `{ "matches": [{ "recipe", "have", "missing", "expiring" }] }`: the member's own and published recipes the pantry covers at least half of, fewest missing first, then those that use what expires within three days, leaving out what the member avoids. `have`, `missing` and `expiring` are the recipe's own ingredient names. Water, salt, pepper, ice and cooking oil count as in every kitchen. `POST /recipes/:id/groceries` and `POST /planner/groceries` take `"skipPantry": true` to leave those and what the pantry covers off the list, and then also answer `skipped`, the names they left off; without it, every line goes on the list as before.

## Ordering groceries

When the server has an Instacart key (`"groceryCheckout": "instacart"` in `/v1/capabilities`), `POST /groceries/checkout` sends the unchecked lines of the member's list (their household's, in one) to Instacart and answers `{ "url", "provider": "instacart", "items" }`, a page where the cook picks a store and checks out; `POST /recipes/:id/checkout { "servings", "skipPantry" }` does the same for a recipe's ingredients, scaled, leaving off what the pantry has, as an Instacart recipe page that links back to the recipe. Quantities in units Instacart counts in (cups, spoons, grams, ounces, pounds, cans…) go with each line; others (a clove, a pinch) leave Instacart to offer one of the product. An empty list is `400`, an unknown recipe `404`, Instacart failing `502` with a sentence that suggests sharing the list instead, and both routes are `404` without a key. Each member can make 20 pages an hour.

## Equipment

The API reads every recipe's step titles and text with an equipment lexicon (`services/api/internal/app/equipment.go` and `equipment_lexicon.go`): about 36 pieces of equipment (pots and saucepans, frying pans, woks, Dutch ovens, sheet pans, baking dishes, loaf, cake, pie and muffin pans, the oven, grill, slow and pressure cookers, air fryer, microwave, blenders, food processor, stand and hand mixers, whisk, grater, mandoline, rolling pin, sieve, colander, thermometer, scale, mortar and pestle, steamer, rice cooker…) with their names in the app's nine languages, and the few verbs that can only mean one ("bake", "sift", "ausrollen"). It is read the way ingredients are ([allergens and diets](#allergens-diets-and-the-pantry)): accents folded and English plurals too, the longest name first, so a Dutch oven is never an oven, a frying pan is one item, "oven-safe" and "pot roast" name nothing, "Ofenform" is a baking dish, and German compounds are read by their head ("Gusseisenpfanne"). A name that is another word elsewhere is read only in its language ("four" is an oven in French, a number in English; "panela" a pot in Portuguese, sugar in Spanish); a recipe without a language reads English ones. `equipmentDetected` lists what the method mentions as English keys (`"frying pan"`, `"oven"`), in the order it first does, at most 20; the app names them in the reader's language and shows them only when the author lists none, labelled as found in the method. It reads names, not cooking: a tool the method takes for granted isn't there, and a bare English "pan" names nothing, since it may be any pan (one the method says more about does: "a dry pan" is a frying pan, "a pan of water" a saucepan, "pan-fry"), nor do verbs that also mean other things ("blend", "drain", "toast").

A recipe is read again in the same save whenever its steps or language change. A write that changes them without reading them (the seed, an older server) is caught up by a pass at start-up and every ten minutes, as is everything when the lexicon changes (`equipmentVersion`).

What a method takes for granted, and when, is guessed. Recipes the API returns carry `equipmentGuess`: for a recipe whose author lists no equipment, `[{ "key", "steps" }]`, each piece its method likely uses (keys as `equipmentDetected` has them) with the 1-based steps that use it, in the order the method first uses them; `[]` for a recipe with a list, one not guessed about yet, or one whose steps changed since. Once per version of a published recipe without a list, the cheap translation model (GPT-6 Luna through OpenRouter) reads the title and steps and answers from the lexicon's keys only, so the app names every piece in the reader's language ("cook the linguine in salted boiling water" is a pot at that step, "blend until smooth" a blender); what the method names is added at the steps that name it. At most `EQUIPMENT_GUESS_RECIPES` (200) recipes a day, the most saved first, under an advisory lock, each reserving its cost against the shared free budget like a translation (`reserveShared`, `ai_usage` kind `equipment_guess`, no member pays; about a twentieth of a cent a recipe). What it answers is checked: only offered keys, only the recipe's steps, each piece once, at most 20. A request that reached the provider isn't sent again for that version, answered or not. Without an OpenRouter key, or with the day's cap or budget spent, recipes show what their method mentions. The app shows the author's list, else the guess (labelled as the sous-chef's), else what the method mentions; cooking mode names under each step what the guess says it uses. Cooking questions, the live sous-chef, `get_recipe` and the assistants' recipe card read the guess with its steps.

`POST /recipes/equipment` (a session needed) answers what a method mentions before it is saved, for the editor's **Add what the method mentions**: it takes `{ "steps": [{ "title", "text" }], "language" }` (up to 40 steps; `language` one of the nine or `""`, else `400`) and answers `{ "equipment": ["frying pan", "oven"] }`, keys as `equipmentDetected` has them. Nothing is saved and no AI is asked.

Imports read schema.org `tool` (HowToTool items or their names, or one text listing them) into `equipment`, keeping names of up to 60 characters and at most 20; recipe jobs (pages without recipe data, video captions) and the sous-chef's drafts ask the model for it in the same shape. The recipe pages' schema.org data lists the author's `equipment` as `tool`.

## Uploads

`POST /media/uploads` takes `{ "kind": "image" | "video" | "audio", "contentType", "size" }` (JPEG, PNG, WebP, MP4 or WebM, up to 50 MB; a [family recording](#family-recipes) as `audio/mp4`, `audio/webm` or `audio/mpeg`, up to 25 MB; 60 an hour per account) and answers `{ "uploadUrl", "method": "PUT", "headers", "url", "key", "expiresAt" }`. The app PUTs the file to `uploadUrl` within 15 minutes, sending exactly `headers`, then calls `POST /media/uploads/complete { "key" }`, which checks the stored file and answers `{ "url" }` (`404` if the key isn't the account's or nothing arrived, `400` for a file that isn't what it said, which is deleted). Browsers need the bucket's CORS rules ([storage](STORAGE.md)). The older multipart `POST /media` still works and streams large files to storage; it allows 5 minutes for the body.

A step may have an `image`, a photo of that step, and a `video`, a short clip of it (uploaded, or made by AI: [step clips](#step-clips)), under the same rules as the recipe's own photos and video (in production, our storage or `MEDIA_HOSTS`; media the recipe already has stays valid). Steps without one have no `image` or `video` key. On an update, a step that leaves either key out (as older apps and the sous-chef do) keeps the photo or clip of the saved step with the same text, or else of the step in the same place with the same title; `""` removes it. A step of a [family recipe](#family-recipes) may also have a `voice`, kept the same way (`null` removes it).

Two optional fields link a recipe to where it came from. Leaving a field out (as older apps do) or sending `null` keeps a saved recipe's value; `""` removes it.

- `sourceUrl`: the page an imported recipe came from, an `http` or `https` address of up to 500 characters (`400` otherwise).
- `derivedFrom`: the id of the recipe this one adapts, which must be published or one of the author's own, and not the recipe itself (`400`). The link a recipe already has stays valid after its original is unpublished. The `{ id, title, author }` object recipe JSON carries is accepted and ignored, so a recipe can be sent back as it was loaded. Deleting the original removes the link, not the variation.

Recipe JSON also has `sourceUrl` (`""` for none), `derivedFrom` (`{ "id", "title", "author": { "id", "name", "handle" } }` while the original is published and its author in good standing, else `null`), and `variationCount` (published variations), `commentCount` and `cookedCount`. Like `reviewCount`, the counts include what suspended members wrote, which their lists leave out. `verifiedCooks` counts the recipe's [verified cooks](#cook-sessions-and-the-creator-fund), and `cookedMinutes` is how long they usually take (the median of the latest 500, in whole minutes), or `null` until there are 3. `improvedBy` counts the cooks whose [fixes](#recipe-fixes) its author accepted. The recipe's `author` carries `founding`: `true` for a [founding creator](CREATOR-FUND.md#founding-creators), whom the app names on the author line. Creators (`GET /creators`, `GET /creators/:id`, a cookbook's `owner`) and `GET /me` carry it too.

## Variations

`GET /recipes/:id/variations` lists up to 20 published recipes whose `derivedFrom` is this recipe, newest first, in the usual recipe shape.

## Recipe translations

`GET /recipes/:id/translation?language=fr` answers a recipe's text in one of the app's nine languages: `{ "language", "sourceLanguage", "title", "description", "ingredients": [{ "name" }], "steps": [{ "title", "text" }], "equipment", "translatedAt" }`, with exactly the recipe's ingredients and steps, in its order, and `equipment` name for name when the author lists any (left out otherwise). Amounts, units, timers, media, tags and cuisine aren't in it: they stay as the recipe has them, and the app lays the translated words over the recipe it shows. The recipe must be published, or the caller's own, by a cook in good standing (`404`), and `language` one of the nine (`400`). A recipe already written in that language answers with its own text and `translatedAt: null`, without AI.

A recipe is translated into a language once, by `OPENROUTER_TRANSLATION_MODEL` (GPT-6 Luna unless set), and the translation is kept for every later reader, guests included. It is kept under a digest of the recipe's text and language, so editing the recipe's text has the next reader's request translate it again; a translation of other text is never answered. The model gets the recipe as JSON data with rules never to follow instructions in it and to keep its shape; an answer with another number of ingredients, steps or equipment names, a field left out, or text far longer than what it translates is refused.

Making a new translation needs a session (a guest gets `401` "Sign in to translate this recipe.") and text AI (`503`), and allows 30 a member an hour (`429`); reading one already made is free and open to everyone. Every reader shares it, so no member pays: it is reserved against the shared free daily budget, like free members' use (`429` when that or the day's budget is spent, `503` while AI is paused from the admin console), and settled to the cost OpenRouter reports. Requests for the same translation wait on one model call (up to 90 seconds), on one API process and, through a database lock, across replicas; four translations run at once per process (`503` "Translation is busy…" past that). A failed one is `502` ("We couldn’t translate this recipe. Please try again."), and for 30 seconds asking again answers the same rather than paying again; the app never repeats the request on its own. A translation nobody has read for 90 days is deleted, and deleting the recipe deletes its translations. `/capabilities` reports `recipeTranslation` and `translationModel`.

## Importing a recipe

`POST /recipes/import` takes `{ "url" }` and reads a recipe from that web page into a private draft for the editor; nothing is saved. It needs a session and allows 20 imports an hour per member. The address may be `http` or `https` (the scheme may be left out); pages are fetched over HTTPS from public addresses only, following up to four redirects, reading at most 3 MB of an HTML page.

- A page with schema.org `Recipe` data (JSON-LD) answers `200` with `{ "method": "structured", "recipe": <recipe input> }`: `published: false`, `aiGenerated: false`, and `sourceUrl` the page it ended at (without its fragment or tracking parameters). Ingredient lines become amounts, units and names, and its `tool` the `equipment` ([equipment](#equipment)); missing times, servings or descriptions are filled in. Its photos are kept only where a recipe may show them, so in production they're usually left out.
- Otherwise, with text AI on, it answers `202` with `{ "method": "ai", "job": <AI job> }`: an ordinary `recipe` job, under the same allowances and budgets as `POST /ai/jobs`, whose prompt holds the page's text. An `Idempotency-Key` header (8–100 characters) makes a retry answer the same job; without one, every request queues a new job. Poll `GET /ai/jobs/:id`; the finished `result.recipe` has the page as its `sourceUrl` and `aiGenerated: true`. A job that finds no recipe on the page fails with "We couldn’t find a recipe on that page."
- An address that isn't one is `400`; a page that can't be opened `502` ("We couldn’t open that page."); a page that isn't HTML, or has too little text to hold a recipe, `422` ("We couldn’t find a recipe on that page."); a page without recipe data while text AI is off `503` ("We couldn’t read a recipe from that page.").
- A failed import job never counts against the member: its reservation is released (`estimated_cost` 0), so it counts neither toward the plan's sous-chef messages nor toward its 30-day AI allowance. When the model did read the page, that cost moves to the shared `ai_usage` ledger (`kind` `unread_import`, no member), so the day's budgets still count it.

### Video and photo posts

The same endpoint takes a link to a post on TikTok (`/@user/video/…`, `/photo/…`, and the `vm.`/`vt.tiktok.com` and `/t/` short links), Instagram (`/p/`, `/reel/`, `/reels/`, `/tv/`, `/share/…`), YouTube (`watch?v=`, `/shorts/`, `/live/`, `youtu.be`), Facebook (`/reel/`, `watch?v=`, a page's `/videos/` and `/posts/`, `permalink.php`, `fb.watch` and `/share/…`) or Pinterest (`/pin/…` on any `pinterest.*` domain, and `pin.it`). Other addresses on those sites, such as a profile, are read as ordinary pages. Short links are followed through the same public-address guard as pages, stopping at the first post address. No platform keys are used; the import reads what the creator wrote, the caption:

- TikTok: its public oEmbed answer (the caption and the account). YouTube: the whole description from the player data on the watch page (sent with a consent cookie), else the page's `og:description`, with oEmbed for the channel. Instagram and Facebook: the public post page's `og:description`, `og:title` and description, without the likes, comments and date around the caption. Pinterest: the page the pin was saved from, then the pin's description and who pinned it (its JSON-LD).
- A recipe page the caption links to ("full recipe at …", at most two, skipping other platforms and link-in-bio or shop sites) is imported instead when it has recipe data, crediting that page as `sourceUrl` and the creator in the description ("Shared by Chef Jo (@chefjo) on TikTok."). Otherwise a caption that could hold a recipe (an "Ingredients" line, or at least two ingredient-like or numbered lines) becomes a `recipe` job; failing that, a linked page's text does.
- A caption job's prompt starts `Import the recipe in this post’s caption: <post>` and names the creator on its second line. The model is told the caption is data, not instructions; to keep the creator's quantities exactly; to say in the description which amounts it estimated; and to credit the creator, which the worker adds ("From Chef Jo (@chefjo) on TikTok.") if the model doesn't. The result's `sourceUrl` is the post's canonical link (no tracking parameters) and it carries none of the post's photos or video.
- A caption without a recipe is `422` ("We couldn’t find a recipe in that post’s caption. Try the link to the full recipe if the creator shared one."), as is a caption job whose model finds none. A post that can't be read (private, signed-in only, removed, or a short link that leads nowhere) is `502` ("We couldn’t open that post. It may be private or no longer available."). Captions are capped at 6,000 characters, oEmbed answers at 256 KB, and the post itself gets 10 of the import's 20 seconds.

## Bulk imports

Many recipes at once, read on the server into private drafts one at a time, so the cook can leave meanwhile ([switching](SWITCHING.md)). A batch is `{ "id", "purpose", "site", "createdAt", "finishedAt", "permissionAt", "items": [{ "position", "url", "text", "status", "error", "recipe": { "id", "title", "image" } | null }] }`: `text` is a pasted recipe's first line, `status` is `queued`, `reading`, `imported` or `failed`, `error` says why a failed item brought nothing, and `recipe` is the draft it became while that exists.

- `POST /imports` (a session; 10 an hour per member) takes `{ "purpose", "urls", "texts", "ownRecipes" }` and answers `201` with the batch. `purpose` is `links` (the default; Add a recipe), `mealime` (the page for Mealime's members) or `own_site` (a creator's own site). `urls` are links as `POST /recipes/import` takes them, a repeat read once; `texts` are recipes the member wrote. A batch holds up to 50 items, of which up to 10 texts of up to 12,000 characters; an `own_site` batch takes only links on one site (`www.` aside, `site` records it) and needs `"ownRecipes": true`, the member's confirmation, which the batch records with the statement and `permissionAt`. A link to `mealime.com` fails at once ("This is one of Mealime’s own recipes, …") and is never fetched; a batch of only those is finished already. Anything else malformed is `400` with its reason; a fourth unfinished batch, or more than 200 items in 24 hours, is `429`.
- `GET /imports` lists the member's five latest batches, newest first (`?purpose=` keeps one kind); `GET /imports/:id` answers one (`404` for anyone else's). `POST /imports/:id/stop` fails the items still waiting ("You stopped the import before this one was read.") and answers the batch; one being read finishes.
- The worker reads one item of a batch at a time, batches taking turns. Recipe data, or pasted text laid out with Ingredients and Method lines, is saved at once; anything else becomes an ordinary `recipe` job (`Idempotency-Key` `import-batch-<batch>-<position>`), under the plan's allowances like `POST /recipes/import`'s, and is saved when it finishes. These jobs are left out of `GET /ai/jobs`. An item that brings no recipe never counts against the member, as with a single import; what the model may have cost goes to the shared ledger. An `own_site` item's recipe photo is copied into the member's storage. A finished batch is deleted after 90 days, except an `own_site` one.
- `POST /imports/similar` (no session needed; 10 a minute per visitor address) takes `{ "names" }`, 1–25 recipe names (repeats once), and answers `[{ "name", "recipes": [<recipe>] }]`: up to three published recipes like each, from the ordinary search (the whole name, then its last words), for Mealime's own recipes, which can't come over.

## Comments

`GET /recipes/:id/comments?offset=&limit=` (up to 50, the default) lists a recipe's comments oldest first, as `{ "id", "body", "parentId", "createdAt", "updatedAt", "author": { "id", "name", "handle", "avatar" }, "canDelete" }`. Replies are in the same list, with the `parentId` of the comment they answer (`null` for a comment). The recipe must be published, or the caller's own; comments by suspended members, and the replies to them, are left out. `canDelete` is true for the caller's own comments and, for a recipe's author, every comment on it.

`POST /recipes/:id/comments` takes `{ "body", "parentId" }` (1–1,000 characters; `parentId` optional) and answers `201` with the comment. It needs a session and a published recipe (`404`), and allows 30 comments an hour per member. Replies are one level deep: replying to a reply answers the comment it replies to; a `parentId` that isn't a comment on this recipe is `404`. `DELETE /comments/:id` lets a comment's author, or the recipe's, remove it and its replies (`204`, else `404`). Admins remove comments with `DELETE /admin/comments/:id` ([admin console](ADMIN.md#api)).

## I cooked this

`POST /recipes/:id/cooked` takes `{ "photo", "note" }`, both optional, and answers `{ "cooked": true, "cookedCount" }`. There's one per member and published recipe (`404` otherwise): cooking it again moves it to the top and keeps whichever of `photo` and `note` it doesn't send. The photo follows the rules for recipe photos (`400`), and the note is up to 500 characters. `DELETE /recipes/:id/cooked` answers `204`. `GET /recipes/:id/cooks?limit=` (up to 30, the default; `offset` pages) lists who cooked a published recipe, most recent first, as `{ "id", "photo", "note", "createdAt", "author": { "id", "name", "handle", "avatar" } }`, leaving out suspended members. `GET /library` includes `cookedIds`.

## Cook sessions and the creator fund

Cooking mode records a session for a signed-in member; the rules and the money are in [creator fund](CREATOR-FUND.md). A session is `{ "id", "recipeId", "steps", "stepReached", "startedAt", "finishedAt", "verified", "mealId" }`, `mealId` naming the [meal](#meal-timeline) it was cooked in, or `null`.

- `POST /recipes/:id/cook-sessions` (no body; 60 an hour per member) starts one on a published recipe or the member's own and answers `201` with it; anything else, or a recipe without steps, is `404`.
- `PATCH /cook-sessions/:id` takes `{ "step", "finished" }`, both optional: `step` (1-based, 0–1000, else `400`) raises the furthest step reached, never lowers it, and is capped at the recipe's step count; `"finished": true` ends the session and decides `verified`. It answers the session. A finished session doesn't change, and asking again answers it as it is; one started more than 24 hours ago is `409`; someone else's is `404`. An "I cooked this" post is separate and never makes a session verified.
- `GET /me/earnings` (while `/capabilities` reports `creatorFund`, else `404`) answers `{ "month", "cooks", "estimateCents", "balanceCents", "paidCents", "sharePercent", "minimumCents", "firstPayoutAt", "history", "payouts", "countries" }`: this UTC month's verified cooks of the member's recipes and their earnings so far, unpaid and paid earnings of closed months, when the creator's first payout may go while it's still ahead (60 days after their first month closed; `null` otherwise), the 24 latest months as `{ "month", "amountCents", "cooks", "status": "pending" | "paid", "paidAt" }`, the payout setup `{ "connected", "enabled", "detailsSubmitted", "held", "country" }`, and the two-letter countries Stripe can pay out to. Amounts are integer US cents. `?refresh=true` re-reads the payout account from Stripe first.
- `POST /me/payouts/onboarding` takes `{ "country" }` (two letters, needed only the first time) and answers `{ "url", "kind" }`: Stripe's Express onboarding (`"onboarding"`, creating the account the first time), or the Express dashboard once onboarding is done (`"dashboard"`). It returns to `APP_URL/?page=profile&payouts=done`, or `&payouts=refresh` when the link expired. It's `503` while the fund is off, `403` for a member with no published recipe and no earnings, `400` without a country, `422` for a country Stripe can't pay out to, and `502` when Stripe fails.
- `POST /payouts/webhook` is for Stripe's Connect events. It requires a `Stripe-Signature` signed with `STRIPE_CONNECT_WEBHOOK_SECRET` (the same scheme as the billing webhook; `400` otherwise), re-reads the account of each `account.updated` and records whether payouts are enabled, and answers `200` to other events. It's `404` while the fund is off or the secret isn't set.

## Cook-tested recipes

What cooking mode records about each step, and what recipes show from it; the rules are in [cook-tested recipes](COOK-TESTED.md).

- `POST /cook-sessions/:id/events` takes `{ "events": [{ "seq", "kind", "step", "at" }] }`, 1–50 a request (else `400`): `kind` is `enter`, `leave`, `timer_start`, `timer_pause` or `timer_end`, `step` is 1-based (1–100), `seq` (0–100,000) is the app's own count of the session's events, so a retried one is kept once, and `at` is the app's clock in milliseconds. It answers `204` whether or not it kept them: nothing is kept for a session over 24 hours old or finished more than 10 minutes ago, past 600 events, past the recipe's last step, or for a member who keeps their cooking out. Someone else's session, or one on the member's own recipe, is `404`. Members may send 120 a minute.
- `GET /recipes/:id/insights` (no session needed) answers a published recipe's, or the member's own: `{ "sessions", "finished", "finishRate", "steps", "computedAt" }`. `sessions` are those that are over (finished, or a day old) and `finishRate` is `finished / sessions` from 20 of them, else `null`. `steps` has only steps with something to say, by their place in the recipe as it is now: `{ "step", "sessions", "medianSeconds", "p75Seconds", "timerSeconds", "note", "questions" }`, where numbers show from 5 sessions, `note` is `{ "kind": "longer" | "usual", "minutes" }` or `null`, and `questions` are up to two `{ "id", "question", "answer", "checked" }` that 3 cooks asked (`checked` when the answer is the author's). `404` otherwise. Numbers are the last nightly pass's.
- `GET /recipes/:id/insights/author` is the recipe author's view (`404` for anyone else): the same plus `verifiedCooks`, `cookedMinutes`, and every step, each with `entered` and `gaveUp` (sessions that reached it and stopped there, from 5) and all its questions asked by 3 cooks, hidden and unanswered ones included, with `askers` and `hidden`.
- `PATCH /recipes/:id/insights/questions/:question` is the author's: `{ "answer" }` (2–1,000 characters, else `400`) replaces the answer with theirs, `{ "approve": true }` keeps the sous-chef's as theirs, and `{ "hidden": true | false }` hides it from cooks or shows it again. It answers the question; another recipe's, or someone else's, is `404`.

## Recipe fixes

Changes cooks who made a recipe suggest, and its author's answer; the rules are in [recipe fixes](RECIPE-FIXES.md). A suggestion is `{ "id", "kind", "part", "place", "before", "after", "reason", "status", "fits", "votes", "voted", "mine", "createdAt", "author": { "id", "name", "handle", "avatar" } }`: `kind` is `time`, `heat`, `note` (a `step`'s `{ "title", "text", "seconds" }`), `missing_step` (a `new_step` after `place`, `0` for the start) or `amount` or `swap` (an `ingredient`'s `{ "name", "amount", "unit" }`); `place` is where its part is now (when it `fits`) or was; `status` is `open`, or `stale` once it waited 30 days; `votes` are the other cooks who said "same for me".

- `GET /recipes/:id/suggestions` (no session needed) answers a published recipe's `{ "canSuggest", "suggestions" }`, the most agreed first; `canSuggest` is whether the caller has a verified cook of it and isn't its author. `404` otherwise.
- `POST /recipes/:id/suggestions` takes `{ "kind", "step" | "ingredient", "change", "reason" }` (`step` 1-based, or the step a missing one goes after; `ingredient` 1-based; `change` the fields that change; `reason` up to 500 characters) and answers `201` with the suggestion. It's `403` without a verified cook of the recipe or for its author, `400` for an unknown kind or part, no change, or a recipe the editor wouldn't save, and `409` while the caller's suggestion for that part waits. 20 an hour per member.
- `PUT /suggestions/:id/vote` is "same for me" from another verified cook (`403` otherwise, `400` for one's own) and `DELETE /suggestions/:id/vote` takes it back; both answer the suggestion. `DELETE /suggestions/:id` withdraws the caller's own (`204`).
- `PATCH /suggestions/:id` is the recipe author's answer: `{ "action": "accept", "change" }` (`change` optional, when they edited it) saves the recipe and answers its version, or `{ "action": "decline", "response" }` (up to 500 characters) answers `204`. Accepting one whose part changed since is `409`; another recipe's is `404`.
- `GET /recipes/:id/history` (no session needed) answers `{ "versions": [{ "id", "number", "kind", "part", "before", "after", "createdAt", "by", "undoable", "suggestionId" }] }`, the accepted fixes newest first; `undoable` is true for the author's latest while nothing changed the recipe since. `POST /recipes/:id/history/:version/undo` restores the ingredients and steps from before it (`204`; `409` once the recipe changed since).

## Meal timeline

Two to four recipes cooked together so they're ready at once ([meal timeline](MEAL-TIMELINE.md)). Both routes need a session.

- `POST /meals/timeline` takes `{ "recipes", "eatAt", "timeZone", "kitchen" }`: 2 to 4 different recipe ids (else `400`), each published by a cook in good standing or the caller's own (else `404`); when to eat, as RFC 3339 or a local `2026-10-17T19:30` read in `timeZone` (an IANA name, UTC when left out; `400` for another), from 12 hours ago to 60 days ahead (else `400`); and optionally `{ "burners", "ovens" }` (1–12 and 1–3, else `400`; 4 and 1 when left out). It answers the plan, times in RFC 3339 in that zone: `{ "eatAt", "startAt", "kitchen", "dishes", "steps", "free", "warnings" }`. `dishes` are `{ "recipeId", "title", "image", "startAt", "readyAt", "estimated", "tested" }` in the order asked. `steps` are every step of every dish, in the order they start: `{ "recipeId", "step", "title", "startAt", "endAt", "active", "wait", "oven", "burners", "preheat", "estimated", "tested" }`, `step` 1-based, seconds in whole minutes, `oven` in °C, `preheat` for a step that heats the oven ahead of an oven step (it starts 15 minutes before it), `tested` when 5 cooks' median time replaced the written one and `estimated` when its times are an estimate. `free` is `{ "startAt", "endAt" }` for each stretch of 5 minutes or more with nothing hands-on to do. `warnings` are what the kitchen can't do, never a step left out: `{ "kind": "oven", "at", "recipeIds", "heats" }` (heats at once in °C, more than it has ovens), `{ "kind": "burners", "at", "recipeIds", "needed", "have" }`, and `{ "kind": "hands", "at", "recipeIds", "minutes" }` (cooked food waiting that long because the cook's hands were busy). Nothing is saved and no AI is asked. Members may ask 120 an hour.
- `POST /meals/cook-sessions` takes `{ "recipes" }` (2 to 4, as above) and answers `201` with `{ "mealId", "sessions" }`: a [cook session](#cook-sessions-and-the-creator-fund) for each recipe that counts (published, someone else's), linked by `mealId`, which sessions then carry. The caller's own recipes get none. Each session is updated, finished and sent step events as cooking one recipe does. Members may start 30 an hour.

## Shared cookbooks

Cookbooks are private until their owner shares them. `GET /library`'s `collections` have `public`, `description` and `household`. `PATCH /collections/:id` takes any of `{ "name", "public", "description", "household" }` (a name of 1–60 characters, a description of up to 300) and answers `{ "id", "name", "public", "description", "household" }`; what it doesn't send stays. `household: true` shares it with the owner's household ([family recipes](#family-recipes)); outside a household that's `409`. Another member's cookbook is `404`, and a name the owner already uses `409`.

`GET /cookbooks/:id` needs no session and answers `{ "id", "name", "description", "public", "household", "owner": <creator>, "recipeCount", "recipes", "hasMore" }` for a shared cookbook, for its owner's own, or for one shared with the viewer's household; anything else is `404`, as is a suspended owner's. It shows the published recipes of cooks in good standing, and to its owner and their household the owner's private recipes in it, newest saved first; `limit` (up to 100, default 60) and `offset` page them. `GET /creators/:id/cookbooks` lists a cook's shared cookbooks that show any recipes, most recently added to first, as `{ "id", "name", "description", "recipeCount", "cover" }` (the photo of the newest pictured recipe, or `""`). The web app opens a cookbook at `/cookbooks/<id>`, and `GET /sitemap` lists shared cookbooks with recipes as `cookbooks: [{ "id", "updatedAt" }]`.

## Family recipes

A relative's recording, or a photo of a handwritten card, written down as a private recipe whose steps play what the relative said ([family recipes](FAMILY-RECIPES.md)). `GET /capabilities` has `familyRecipes` when AI and storage are set up.

- `POST /recordings` takes `{ "url", "speaker", "durationMs" }`: a recording the member [uploaded](#uploads) with `kind: "audio"`, whose voice it is (1–60 characters, on one line), and its length (3 seconds to 30 minutes; `0` for a file the app couldn't time, whose size stands in). It keeps the recording twice and queues a `recipe` [job](#ai-jobs) that writes it down, with an optional `Idempotency-Key`, and answers `201` with `{ "recording", "job" }`; `job` is `null`, with `error` saying why (AI off, an allowance used), when it can't start now, and the recording is kept either way. The same `url` again answers `200` with the recording it made. A member keeps up to 200 (`409` past that).
- A recording is `{ "id", "speaker", "url", "durationMs", "language", "consentedAt", "createdAt", "recipe": { "id", "title", "published" } | null, "job": { "id", "status", "error" } | null }`. `GET /recordings` lists the member's, newest first. `PATCH /recordings/:id { "speaker" }` renames whose voice it is. `DELETE /recordings/:id` deletes it, both its copies and its clips from its recipe (`204`).
- `POST /recordings/:id/transcribe` writes down again a recording that isn't a recipe (its job failed, AI was off, its recipe was deleted), from the transcript it already has when there is one: `202` with the job, `200` with one still running, `409` while it is a recipe.
- `POST /family/cards { "url" }` takes a photo of a card the member uploaded (JPEG, PNG or WebP) and answers `202` with a `recipe` job whose `source` is the photo.
- A finished family job's `result` is `{ "recipeId", "title" }`: the recipe is saved, private and AI-assisted; a card's has the photo as its cover. A job that brings no recipe fails with a reason and doesn't count against the member, like an import.
- Recipe JSON has `recordings`: `[{ "id", "speaker", "url", "durationMs", "consented" }]` (`[]` for most recipes), and a voiced step `voice`: `{ "recording", "startMs", "endMs" }`, the stretch of one of the recipe's own recordings that says it (any other is dropped when the recipe is saved).
- Publishing a recipe with a recording nobody agreed to is `409` ("Before publishing, confirm that the person you recorded agreed to share their voice."). `POST /recipes/:id/recording-consent { "agreed": true }` records the author's confirmation and answers `{ "recordings" }`; `agreed: false` is `400`, someone else's recipe `404`.
- `PUT /recipes/:id/save` also takes the member's own private recipes, so they can be kept in a cookbook. `GET /household/cookbooks` lists the cookbooks the member's household shares, theirs included: `[{ "id", "name", "description", "recipeCount", "cover", "owner": { "id", "name", "handle", "avatar" } }]` (`[]` outside a household). A private recipe in one opens for every member of the household: `GET /recipes/:id`, narration, translation, cook sessions, hands-free questions, the planner and the grocery list.

## AI jobs

`POST /ai/jobs` makes a photo from a description (the editor's Create a cover photo). It takes `{ "kind": "image", "prompt": "Overhead editorial shot of a lemon pasta" }` and an `Idempotency-Key` header between 8 and 100 characters. A new request returns `202` and a job object; retrying the same payload with the same key returns the same job. Reusing a key for different input returns `409`. Any other kind is `400`: questions, twists, swaps, nutrition, meal plans and new recipes are the sous-chef's conversation, and a `recipe` job is made only by importing a page (above). Unconfigured providers return `503`; exceeded quotas return `429`. Released apps' Create a short clip still sends `kind: "video"`, which makes one clip like a step's (below) and counts as one.

Poll `GET /ai/jobs` for the current account's latest 30 jobs (leaving out a [bulk import](#bulk-imports)'s, whose recipes are saved already), or `GET /ai/jobs/:id` for one. Status progresses from `queued` to `running`, optionally `processing` for a clip, and then `completed` or `failed`. Results contain `url` (a photo or clip), or `recipe` for an import; jobs from before those moved to the sous-chef can hold `text`. Step clips are jobs of kind `clip`. Generated recipes are editable private drafts; generation never publishes on the user's behalf.

### Step clips

`POST /recipes/:id/step-clips`, with an `Idempotency-Key`, orders an AI clip of every step of the member's own recipe that has no clip and none on its way (one per step text): four silent seconds at 720p, 16:9, from Seedance 2.0 Mini Eco on reAPI, with the provider's AI watermark. A step with a photo has it as the clip's opening frame. Only the cook asks for them: the editor's Make step clips, or the sous-chef's `generate_recipe_media` with `step_clips` when the member asks; nothing makes them on its own. The request reserves a clip for each step at once, and with paid plans needs that many left in the plan (`429` "Your plan's AI step clips left for the last 30 days don't cover every step of this recipe." otherwise); a refusal queues none. It answers `202` with `{ "clips": [{ "text", "status", "error", "url"? }] }`; the same key again answers `200` with the recipe's clips and orders nothing, and a key used for another recipe is `409`. Someone else's recipe is `404`, a recipe whose every step has a clip or one on its way `409`, and a server without reAPI or storage `503`.

`GET /recipes/:id/step-clips` lists the clips of the member's recipe ordered in the last day, the latest for each step text, in the same shape. Each finished clip goes onto the saved step with the same text that still has no clip, wherever it has moved, and marks the recipe AI-assisted; a step that was rewritten, or got a clip of its own meanwhile, keeps what it has, and the clip stays in the member's AI history.

`POST /media/touch-up` takes `{ "url", "kind": "avatar" | "dish" }` and an `Idempotency-Key`, and queues an AI retouch of a photo the member already has: one they uploaded or generated, or the profile photo they use now (such as their Google picture). It answers `202` with an `image` job whose `source` is that photo; the result's `url` is a new photo, and the original is left as it is. The image model gets the photo as a reference and is told to keep the subject exactly as it is while improving light, color and focus. It counts as an AI photo for plan allowances and reserves the same budget. Anything else is `400`.

## Cooking narration

Both routes need a session and a recipe that is published or the caller's own; `:step` is the zero-based step index (0–99, else `400`), and a missing recipe or step is `404`. `POST /recipes/:id/steps/:step/narration` takes `{ "text" }`, which must equal the saved step text (`409` otherwise), and answers `{ "path", "model" }`, where `path` is the audio route relative to `/v1`. A blank step or one over 4,000 characters is `422` (use device speech), and `503` means narration is unconfigured or busy. An uncached step starts generating in the background, where plan allowances and AI budgets are checked, so a refusal shows up as a failed GET (`502`) rather than a `429`. A cook reading the recipe [translated](#recipe-translations) also sends `"language"`: `text` must then equal the step of the recipe's current translation into that language (`409` when there is none, or it is of an older version), the answered `path` ends in `?language=fr`, and the GET reads that step the same way. Without it, as older apps send, the recipe's own text is read.

`GET /recipes/:id/steps/:step/narration/:key` answers `audio/mpeg` and never starts a generation; a stale key (the step text, voice or model changed) is `404`. Cached audio supports a single byte range (`206`, or `416` for an invalid one). Audio still being generated on the same API process streams as it arrives, but a bounded range such as `bytes=0-1` waits for the whole file; otherwise, as when another replica is generating, the GET waits up to 26 seconds for the shared cache and then answers `504`. A failed generation is `502`. `/capabilities` reports `cookingNarration`; see [cooking narration](COOKING-NARRATION.md).

## Hands-free cooking

`POST /recipes/:id/ask` answers a question asked hands-free in cooking mode ("Chef, how long do I boil it?"); the commands themselves never reach the server ([hands-free cooking](HANDS-FREE.md)). It needs a session and a recipe that is published by a cook in good standing or the caller's own (`404` otherwise), and takes `{ "question", "step", "language" }`: the question as recognized (2–300 characters, else `400`), the 1-based step on screen (`0` for none; past the last step counts as none; outside 0–100 is `400`), and one of the app's nine language codes for the answer (English otherwise). It answers `{ "answer" }`, one to three short sentences meant to be read aloud, from the recipe (its equipment included), that step, and what other cooks found there ([cook-tested recipes](#cook-tested-recipes)). The question is kept with its step for 90 days unless it's the caller's own recipe or they keep their cooking out. The model has no tools and changes nothing. Each question reserves its cost and counts against the plan's cooking questions (`429` with the plan's message when they or the AI budgets are used up); `502` means the model couldn't answer (the reservation stands), and `503` that OpenRouter isn't configured. Members may ask 20 a minute. `/capabilities` reports `cookingQuestions`, and `GET /billing` reports `usage.cookQuestions` and each plan's `cookQuestions`.

## Billing

Plans are sold only through Stripe Checkout on the web ([pricing](PRICING.md)). Every billing route except the webhook needs a session. Until `PAID_PLANS=true`, `GET /billing` is `404`; checkout, the portal and the webhook also need `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. `GET /billing` answers `{ "plan", "status", "interval", "renewsAt", "cancels", "usage", "plans", "checkout", "manage" }`: the plan in effect, the last 30 days' usage, the plan catalog, whether checkout is open, and whether this account can open the customer portal.

`POST /billing/checkout` takes `{ "plan": "plus" | "pro", "interval": "monthly" | "yearly" }` and answers `{ "url" }`, a Stripe Checkout page to open. It is `503` while billing is closed, `400` for `free` or a plan without a configured Stripe price, and `409` when the account already has a paid plan. `POST /billing/portal` answers `{ "url" }` for Stripe's customer portal, or `404` when the account has no Stripe customer or billing is closed. Both return to `APP_URL/?page=profile` (`&plan=welcome` after a completed checkout). Stripe errors are `502`.

`GET /billing` also answers `cancelable`, `refund` and `usageFreesAt`. `cancelable` is `true` when the plan is the member's own Stripe subscription, which they can cancel, keep and refund in the app; it's `false` for Free, a complimentary plan, a housemate's plan and while billing is closed. `refund` is `{ "until", "amountCents", "currency" }` while a yearly plan's payment can be refunded (the first 14 days of its year, a paid invoice, and no refund for the member in the last 12 months), or while a refund is under way; `amountCents` and `currency` (lowercase, as Stripe writes it) are what was paid, left out when Stripe doesn't answer within 5 seconds. Otherwise it's `null`. `usageFreesAt` has a key for each of `usage`'s: when its oldest counted use turns 30 days old and stops counting, or `null` when nothing counts.

`POST /billing/cancel` sets the member's subscription to end when the paid period does (nothing more is charged, and `renewsAt` is when it ends); `POST /billing/resume` undoes that, clearing an end date the portal or the Stripe dashboard set too. `POST /billing/refund` refunds a yearly plan's payment in full and cancels the subscription at once, so the member (and a household on the plan) is on Free. All three answer like `GET /billing`. Each is `404` with a sentence to show when there's no plan of the member's own to change (or billing is closed) and `403` on a housemate's plan; Stripe errors are `502`. A refund is `409` for a monthly plan, after the 14 days, for a year already refunded, an unpaid invoice, a member refunded in the last 12 months, or one already under way; one cut off after Stripe refunded the payment is finished, not repeated, by the next request. Cancelling and keeping allow 30 requests an hour per member, refunds 10.

`POST /billing/webhook` is for Stripe. It requires a `Stripe-Signature` header signed with `STRIPE_WEBHOOK_SECRET` (HMAC-SHA256, timestamp within five minutes; `400` otherwise), handles `checkout.session.completed` and `customer.subscription.created/updated/deleted/paused/resumed` by re-reading the subscription from Stripe, and answers `200` to other events. `DELETE /me` cancels the account's subscription first and stops if Stripe can't confirm.

## Sous-chef

Conversations live under `/recipe-studio`, need a session, and are visible only to their owner; the flow is described in [sous-chef](RECIPE-STUDIO.md#backend-and-persistence). `GET /recipe-studio` lists the 20 most recently updated. `POST /recipe-studio` takes a UUID `Idempotency-Key` that becomes the conversation's `id`, so a retry returns the same conversation; without an OpenRouter key it is `503`. A conversation has `id`, `recipeId`, `title`, `revision`, `status`, `reply`, `error`, `updatedAt`, `recipe`, `voiceSession`, `busy` (a turn is queued or running) and `assets` (the draft's photo and video jobs). `DELETE /recipe-studio/:id` answers `204`: the conversation's messages, photos and media links are erased at once, its usage stays counted for 35 days, and recipes made in it are kept; it is `409` while a voice call is open or closing. A member keeps up to 200 conversations: at the limit, the oldest ones idle for 30 days are deleted to make room, and `POST /recipe-studio` is `409` only when none are.

`POST /recipe-studio/:id/messages` takes `{ "text", "images" }` (1–24,000 characters; up to four image IDs uploaded to this conversation) and an `Idempotency-Key` of 8–100 characters, and answers `202` with `{ "accepted": true }`. Replaying a key with the same input answers the same; different input is `409`, as is a new message while a turn is queued or running. A used plan allowance or AI budget is `429`; AI paused from the admin console is `503`. Poll `GET /recipe-studio/:id?after=<seq>`: the conversation with its `events` after that `seq` (without `after` it has none), up to 1,000, oldest first, as `{ "seq", "role", "content", "imageCount", "actions", "recipes", "changed", "effects", "failed" }` (`changed`: the reply's turn changed the member's data, so the app should refresh its lists; `effects`: what it did, as receipts `{ "kind", "count", "title", "recipe", "page", "undoable", "undone" }`; `failed`: the turn failed or was stopped, and `content` is the server's own sentence); keep paging while a page is full.

`POST /recipe-studio/:id/undo` takes `{ "seq", "index" }`, a reply event and one of its `effects`, and takes it back as far as it still stands: groceries it added (and quantities it merged), a meal it planned (restoring what the slot held), a pantry item it set, a save or follow (either way), a cookbook it created, a check-off. It answers `{ "effects" }` with the receipt marked `undone`; one without `undoable` is `400`, one already undone `409`, and someone else's `404`. The next turn is told what was taken back.

A conversation's `turn` is the reply on its way, `{ "step", "stopping" }`, where `step` names what it is doing (`looking`, `checking`, `kitchen`, `saving`, `recipe`, `media`, or empty while it thinks). `POST /recipe-studio/:id/cancel` stops it: a queued turn never runs and costs nothing; a running one ends at once on the server running it, otherwise at its next step, keeping what it already did. Either way the reply is "Stopped. Your conversation is saved.", marked `failed`. With nothing running it answers `204`, otherwise `202`.

A conversation's `question` is what the sous-chef waits for a yes to: `{ "kind": "action", "seq", "description" }` for an action it proposed (deleting or publishing a recipe, a review, a report, a profile change, deleting a cookbook or several items), or `{ "kind": "publish", "seq" }` after it read back its draft; otherwise `null`. A message can answer it with a tap: `"answer": "yes" | "no"` and `"question": <seq>` beside its `text`. The server then carries out the action (or publishes the draft), or drops it, before the model replies; a `question` that is no longer waiting is `409`. A turn that fails before reaching the model costs nothing and doesn't count against the plan's sous-chef allowance.

`POST /recipe-studio/:id/images` takes multipart `file` (JPEG, PNG or WebP, up to 10 MB, 20 per conversation and 200 per member) and answers `201` with `{ "id" }`, a private source ID rather than a URL; photos over 1600 pixels are stored as smaller JPEGs, and without S3 storage it is `503`. `PUT /recipe-studio/:id/context` takes `{ "screen", "recipeId", "cookingStep", "timeZone", "language", "purpose" }` (`language` is one of the app's nine codes; the sous-chef answers in it when the reply comes from the server; `purpose` is `recipe` when the app opened the conversation from Create a recipe), drops invalid values, and answers `204`. Conversations carry the `purpose` they were last opened for (`""` otherwise). A voice session's status can be `closing` after its DELETE, which already frees the account's one call. `POST /recipe-studio/:id/voice` exchanges a WebRTC offer `{ "sdp" }` for `201` `{ "id", "sdp", "maxSeconds", "remainingSeconds", "model" }`: one call per account at a time (`409`), up to 30 minutes or the plan's remaining voice time (`429` under 15 seconds; `remainingSeconds` is that time when the call starts, so a call with `remainingSeconds` no more than `maxSeconds` ends with the plan's time instead of renewing), `502` if GPT-Live can't connect, and `503` unless `OPENAI_API_KEY` and `OPENROUTER_API_KEY` are both set. `DELETE /recipe-studio/voice/:session` asks that call to end (`204`). `/capabilities` reports `recipeChat`, `recipePhotos` and `voiceAI`.

## Households

A household shares one kitchen: the grocery list, the meal plan and the pantry. Each member is in at most one. `GET /household` answers `null`, or `{ "id", "name", "role": "owner" | "member", "members": [{ "id", "name", "handle", "avatar", "role" }] }` with the owner first, then by when each joined. `POST /household` takes `{ "name" }` (1–60 characters) and answers `201` with the household, its creator as owner; `POST /household/join` takes `{ "code" }` (any case, spaces and dashes ignored) and answers the household. Both move the member's own kitchen into the household's (where the household already has a plan for that day's meal, or a pantry item of that name, the household's stays), and both are `409` for someone already in a household. A wrong, malformed or expired code is `400`, and a household of 20 members is full (`409`). Joining allows 10 tries an hour per member and 30 per address (`429`).

`POST /household/invite` answers `{ "code", "expiresAt" }`: eight characters from A–Z and 2–9, usable by anyone who has it for seven days. Any member can make one; a household keeps its ten newest codes. Codes are stored only as hashes.

`DELETE /household/members/:userId` answers `204`. A member's own id leaves; the owner can remove anyone else (`403` for other members, `404` for someone not in the household). When the owner leaves, the member who joined earliest becomes the owner, and the last one out dissolves the household and keeps its kitchen. A member who leaves starts an empty kitchen of their own; what they added stays with the household. Deleting an account follows the same rules.

While someone is in a household, `GET /kitchen` (its `plans`, `groceries`, `pantry` and `pantryCover`), every `/groceries`, `/planner` and `/pantry` route, `POST /recipes/:id/groceries`, `POST /planner/groceries` and `GET /kitchen/pantry-recipes` work on the household's: any member can plan over a meal, add, check or delete any line, and stock or remove any pantry item. Grocery lines and pantry items carry `addedBy`, and plans `plannedBy`: `{ "id", "name" }` of the member who added it in a household, `null` in a personal kitchen. Another member's private recipe on the shared plan comes as a teaser, `"teaser": true` with its title, photo and times but no description, ingredients or steps; shopping the plan still puts its ingredients on the list, as when its author shops it. The sous-chef's view of the week, its planner and pantry tools and their Undo work on the household's too, and pantry reminders go to every member.

A paid plan covers its household: a member without a plan of their own uses the best one in it (Pro before Plus, then whoever joined first), and everyone on it shares its allowances and spend ceiling. `GET /me`'s `plan` is that plan; `GET /billing` answers it with the pooled `usage`, `sharedBy` (`{ "id", "name" }` of the member whose plan it is, or `null` for one's own) and `sharedWith` (how many others use one's plan). See [pricing](PRICING.md).

A member can share their diets and allergies with their household (`PATCH /me/preferences { "shareDiet": true }`; off until they do, since allergies are health information). Then `GET /me` lists them for the other members under `householdAvoid`: `[{ "id", "name", "avoid" }]`, recipe pages and cards warn everyone about them, and `fits=me`, `GET /kitchen/pantry-recipes` and the sous-chef's searches leave them out for the whole household.

## Preferences

`GET /me` answers `preferences` with every key filled in: `diets`, `allergies`, `units` (`metric`, `imperial`, or `""` to follow the device), `language` (one of the nine app languages, or `""`), `notifications` (`follows`, `pantry`, `reviews`, `comments`, `renewals`, `cookAlong`, each `true` until turned off), `translateRecipes` (`false` until turned on: recipes in other languages open [translated](#recipe-translations)), and `shareCooking` (`true` until turned off: the member's cooking counts toward [cook-tested recipes](#cook-tested-recipes); turning it off also deletes their step events and cooking questions). `PATCH /me/preferences` takes any of `{ "units", "language", "notifications": { "follows", "pantry", "reviews", "comments", "renewals", "cookAlong" }, "translateRecipes", "shareCooking" }`, changes only what it is sent, and answers like `GET /me`; a language tag such as `pt-BR` is stored as `pt`. Other values are `400`. `PATCH /me` changes only `diets` and `allergies`, so the profile form keeps the rest.

`language` is also the language of push notifications.

## Push notifications

`PUT /me/push-token` takes `{ "token", "platform": "ios" | "android" }`, where `token` is the device's Expo push token (`ExponentPushToken[…]`), and answers `204`. The token belongs to the session that registered it: signing out, or the session ending or being revoked, stops that device's notifications, and a token registered by another account moves to it. A member keeps their ten most recently registered devices. `DELETE /me/push-token` takes `{ "token" }` and answers `204`.

Notifications go to the author's followers when a recipe is first published, to a recipe's author for a new review or comment (never their own), to a member whose pantry items expire within two days (once per item, from a daily pass), to a member whose yearly plan renews within the week (once per renewal; an email goes too, whatever the switch says), and to every member once a week for the week's cook-along (never its author). Their text is in the recipient's `preferences.language`, and their `data` is `{ "type": "recipe", "recipeId" }`, `{ "type": "pantry" }` or, for a renewal, `{ "type": "plan" }`. Each kind has a switch in `preferences.notifications`. Sending, limits and setup: [push notifications](NOTIFICATIONS.md).

## Assistants

ChatGPT, Claude and other assistants reach Savorly through the MCP server at `POST /mcp` and link a
member's account through Savorly's OAuth 2.1 endpoints, all at the site's root rather than under
`/v1`: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`,
`POST /oauth/register`, `POST /oauth/token` and `POST /oauth/revoke`. Their requests, answers,
tokens and limits are in [Savorly in ChatGPT and Claude](ASSISTANTS.md). Their access tokens only
open `/mcp`; `/v1` takes sessions, as always.

`GET /oauth/authorize?<an authorization request>` (no session needed) describes a request for the
consent page: `{ "client": { "id", "name", "host", "verified" }, "redirectHost", "localhost",
"scopes" }`, or `{ "redirect" }` when the request can only go back to the app with an OAuth error.
An unknown app, a return address it didn't register, or a link that can't be read is `400` with a
message to show. `POST /oauth/authorize` takes `{ "request": the same query, "approve" }` from the
signed-in member and answers `{ "redirect" }`: the app's return address with a `code` (or
`error=access_denied`), its `state` and `iss`.

`GET /me/connected-apps` lists the member's links, newest first: `[{ "id", "name", "host",
"verified", "scopes", "connectedAt", "lastUsedAt" }]`. `DELETE /me/connected-apps/:id` ends one at

## Analytics

`POST /events` takes `{ "session", "events": [{ "name", "props", "at" }] }` and answers `204`. `session` is a random id the app makes at each launch (1–64 letters, digits, `-` or `_`); up to 50 events per request, 120 requests a minute per address; `at` is optional (ISO 8601; times in the future, or more than a week old, count as now). Names and their properties:

| Name | Props |
| --- | --- |
| `search` | `query` (stored trimmed, lowercase, at most 80 characters), `results` (a count) |
| `recipe_open` | `recipeId`, `from` (optional label) |
| `cook_start`, `share` | `recipeId` |
| `studio_start` | `mode` (label) |
| `onboarding_step` | `step` (label or number) |
| `onboarding_done` | `skipped` (boolean) |
| `import` | `method` (label: `structured` or `ai` for one link, `batch-links`, `batch-mealime` or `batch-own_site` for a bulk import) |

Labels are 1–40 letters, digits, `.`, `:`, `_` or `-`. Unknown names, unknown properties and malformed events are dropped and the rest stored, so a newer app loses only what the server doesn't know; a missing or invalid `session`, or more than 50 events, is `400`. A signed-in member's events carry their account, guests' don't; no IP address or user agent is stored. Events are deleted after 90 days, or with the account.

`GET /admin/insights?days=7|30` (admins; default 7, anything else `400`) answers `{ "days", "topSearches": [{ "query", "count" }], "zeroResultSearches": [{ "query", "count" }], "onboarding": [{ "step", "count" }], "events": [{ "name", "count" }] }`: the 20 most common searches and searches with no results, how many people (members, or launches for guests) reached each setup step, then `done` and `skipped` from `onboarding_done`, and every event's count. The admin console's Overview shows them.
