A full read of the repository (Go API, Expo app, Worker, scripts, docs), the local checks, and a short
live session against the local stack. Findings are ranked within each section; file references point at
the current `main` (`7c8659b`). Nothing here was changed in code: this is a review, not a patch.

The codebase is unusually disciplined for its age: ownership checks on every private mutation, hashed
session tokens, origin checks for cookie mutations, SSRF-guarded downloads, idempotent AI jobs behind
advisory locks, spend reservations with three ceilings, forward-only embedded migrations, and an admin
console with an audit log. The problems below are mostly about scale, operations, and product gaps rather
than correctness of what exists.

## Top priorities

Three correctness bugs first, then the items that most affect cooks, cost and launch readiness. Each has
its detail in the sections below.

- **Bug — the sous-chef silently unpublishes a published recipe.** After `generate_recipe_media` adopts one
  of the user's live recipes, any `save_recipe_draft` forces `published=false` and `aiGenerated=true`
  (`studio.go:512-513`) with no confirmation. See the AI section.
- **Bug — a failed voice handshake burns the member's monthly voice allowance.** The 30-minute reservation
  stays counted when the provider `Create` fails (`voice.go:66-92`, `plans.go:124`); with paid plans on, one
  failure locks a Free member out of voice for a month. See the AI section.
- **Bug — editor drafts collide and never restore for edits.** AI-seeded recipes share the `…new` device
  draft key with hand-started ones and overwrite them; drafts of edits are written but never read back
  (`Editor.tsx:101-105`). See the mobile section.

Then, in order:

1. **Cooking mode lets the phone go to sleep and loses timer alerts in the background.**
   `expo-keep-awake` is only used by the sous-chef voice sheet (`RecipeStudio.tsx:15,250`); `CookMode.tsx`
   never activates it, so the screen dims and locks mid-recipe with wet hands. The step timer is a
   `setInterval` that speaks when it reaches zero (`CookMode.tsx:55-69`); JavaScript timers pause when the
   app is backgrounded or the screen locks and `expo-notifications` is not installed, so a ten-minute pasta
   timer only alerts if the app stays in the foreground. Fix: `useKeepAwake()` while cooking, schedule a
   local notification for `endAt` (cancel on pause/stop), and recompute `remaining` on foreground.
2. **Video uploads above roughly 20 MB cannot succeed on mobile networks.** The editor sends the file
   through the generic client (`Editor.tsx:154` → `api.ts:55`), which aborts every request after 30 s, and
   the Fiber server's `ReadTimeout` is also 30 s (`app.go:82`) while the limit is 50 MB. A 50 MB video needs
   a sustained 13 Mbit/s upload to make it; there is no progress indicator and no resume. Fix: issue a
   presigned PUT to R2 from the API and upload directly from the device (`expo-file-system` upload task with
   progress), then register the resulting URL; or at least exempt `/media` from the 30 s abort and raise
   the server read timeout for that route.
3. **Search is English-only and unindexed beyond the title/description vector.** `recipes.search` is
   `to_tsvector('english', …)` (`001_initial.sql`), and the query ORs in `title ILIKE '%q%'` and
   `ingredients::text ILIKE '%q%'` (`recipes.go:83`), which forces a sequential scan (confirmed with
   `EXPLAIN` locally). Nine UI languages, but "Zitrone" and "лимон" return nothing and "ricota" (typo) returns
   nothing. `pg_trgm` and `unaccent` are available on the server but not installed. Fix: add ingredient
   names and tags to the vector, use the `simple` configuration plus `unaccent` (or detect language per
   recipe), add a trigram GIN index for fuzzy matching, and move the search into one ranked query
   (`ts_rank` + similarity) instead of three ORs.
4. **Shared recipe links have no preview, no crawlable URL and no app hand-off.** Links are
   `https://savorly.cooking/?recipe=<id>` (`RecipeDetail.tsx:219`), the page is a single-bundle SPA, there
   are zero `<a href>` elements and zero semantic headings on a recipe page (checked live), and `index.html`
   has no description or Open Graph tags. The native app registers only the `savorly://` scheme
   (`app.json`), with no `associatedDomains`/`intentFilters`, so a shared https link never opens the app.
   Fix: give recipes a path (`/recipes/<id>`), have the Worker inject `<title>`, description and
   `og:image`/`og:title` from the API with `HTMLRewriter` for that path, render card titles as headings and
   links (`accessibilityRole="header"`/`href` on Pressable), add `robots.txt` and a sitemap, and serve
   `/.well-known/apple-app-site-association` and `assetlinks.json` for universal links.
5. **The API worker polls Postgres about ten statements a second while the container is awake.**
   `runStudioWorker` ticks every second (recover bundles, clean sources, time out actions, a four-statement
   media sync, claim) and `RunWorker` every two seconds (`studio_worker.go:162-192`, `jobs.go:125-160`).
   On Neon this keeps compute awake for the whole 30-minute `sleepAfter` window after the last request and
   adds a steady load that has nothing to do with users. Fix: back off to 15–30 s when a tick finds no
   work, or wake the loops with `LISTEN/NOTIFY` from the handlers that enqueue.
6. **Nothing is ever purged.** Expired `sessions` rows are never deleted (only on logout/reset/admin
   sign-out), `ai_jobs` keep every prompt (up to 12 k characters) and result forever, `voice_events` and
   `narration_usage` grow unbounded, and cooking narration audio is stored as `bytea` in Postgres (up to
   8 MB per step, `008_cooking_narration.sql`). Fix: a daily janitor (delete expired sessions and nonces,
   trim finished `ai_jobs` after 30 days, cap narration cache by age/size), and move narration audio to a
   private R2 prefix with the row keeping only the key.
7. **Signed-in users cannot change their password or email.** `PATCH /me` (`auth.go:178`) takes name,
   bio, avatar, handle and preferences only; the only way to set a password is the "forgot" flow, which
   also needs email delivery configured. Accounts created with Apple/Google have no in-app way to add a
   password (`usablePassword`, `auth.go:128`). Add `POST /me/password` (current password or fresh provider
   token required, revoke other sessions) and an email-change flow with verification of the new address.
8. **The home feed is fixture-coupled and client-computed.** The hero is hard-coded to the seed recipe
   (`Discover.tsx:126`: `recipes.find((r) => r.id === 'lemon-ricotta-pasta') || recipes[0]`), "trending" is
   the most-saved among whatever the first page of 60 newest recipes happens to be, and "From kitchens you
   follow" filters that same page (`App.tsx:832-835`). With a growing catalogue these become wrong quietly.
   Fix: a `GET /feed` that returns hero/trending/quick/following sections ranked server-side (saves in the
   last 7 days, follows), and a `GET /recipes?following=true` for the activity sheet.
9. **"Top rated" ranks a single five-star review above a hundred 4.8s.** `recipes.go:81` orders by the
   plain average. Use a Bayesian average (`(avg*n + m*C)/(n+m)`) or require a minimum count; the same
   applies to the `rating` shown on cards.
10. **No request-level observability or error reporting.** There is no access-log middleware, `recover.New()`
    runs without `EnableStackTrace`, so a panic is logged as a one-line message (`app.go:90`), the request id
    is generated but never included in error bodies, and the app's `ErrorBoundary` reports nowhere
    (`App.tsx:922-942`). Add Fiber's logger (or structured slog per request with the id and user), return
    `requestId` in error JSON so support can correlate, and wire a crash reporter (Sentry works with Expo
    and Workers) before launch.

## Backend and API

- **Shared auth limiter is tighter than it looks.** One `rateLimit(15, 15m)` instance serves register,
  login, forgot, reset and OAuth (`app.go:151-158`), so a person who mistypes a password a few times and
  then requests a reset code can lock themselves out of all five for 15 minutes. Per-route limiters, plus a
  per-account counter for login (currently there is only the per-IP one, so a distributed guess against one
  account is not throttled).
- **Media URLs accept any HTTPS host.** `validMedia` (`models.go:45`) lets a recipe or avatar point at an
  arbitrary external image. That allows hot-linking, tracking pixels keyed per viewer, and content the site
  never stored. In production, restrict `image`, `photos`, `video` and `avatar` to `S3_PUBLIC_URL` (plus
  provider avatars for `avatar`), and keep the permissive rule for development only.
- **No bot protection on registration.** Only the IP limiter stands between the sign-up form and
  scripted account creation; the project already runs on Cloudflare, so Turnstile on `/auth/register` (and
  `/auth/forgot`) is a small change.
- **Sessions are fixed 30-day tokens** (`auth.go:59,63`) with no sliding renewal and no "sign out
  everywhere" for the user (admins have it). Renew on use past the half-life; list/revoke devices in My
  kitchen.
- **`/library` and `/kitchen` are unbounded.** Library returns every saved and authored recipe with full
  ingredients and steps (`kitchen.go:12-19`); kitchen returns every meal plan ever created
  (`kitchen.go:65-70`). Paginate the library and window plans to the visible weeks.
- **Recipe grocery quantities use `%g`** (`kitchen.go:148`), so a third of a cup becomes
  `0.3333333333333333 cup` and large amounts switch to exponent notation; adding the same recipe twice
  duplicates lines. Round to a sensible precision (or fractions) and merge by name/unit.
- **Reviews cannot be deleted by their author**, and there is no review reply or "cooked it" signal;
  `PUT /recipes/:id/review` updates `created_at` on edit, so edits float to the top.
- **Reserved handles** (`handle.go:25`) miss `www`, `mail`, `login`, `signup`, `about`, `privacy`,
  `terms`, `null`, `undefined`, `recipes`, `recipe`, `cook`, `creator`.
- **Default owner email is compiled in** (`operator.go:16`); fine for a single operator, but worth moving
  to configuration only, so a fork or a second deployment never ships with it.
- **Cuisine is free text** at the API (`models.go:58`, 2–60 characters) while the app uses a fixed list
  (`cuisines.ts`); category filters compare exact strings, so "italian" from the sous-chef or an API client
  disappears from the Italian shelf. Validate against the list or normalise case.
- **API responses are not compressed** by the Go server (checked: no `Content-Encoding`). Cloudflare
  compresses at the edge, but the Worker-to-container hop and local/dev traffic would benefit from Fiber's
  `compress` middleware for JSON.
- **Email is used for one thing.** No verification on sign-up (acknowledged in DEPLOYMENT.md), no welcome,
  no notification of password change or new sign-in, no account-deletion confirmation. The Cloudflare
  Email Service client is already there (`email.go`).
- Smaller: `deleteMe` clears the cookie without the `HttpOnly/Secure/SameSite` attributes it was set with
  (`auth.go:257`, harmless but inconsistent); `RecipeInput.Validate` trims title and description but not
  cuisine, tags, ingredient names or step titles; `creators` is capped at 40 with no pagination
  (`recipes.go:171`).

## Database and data

- Add the missing indexes for current filters: `recipes(cuisine) WHERE published`,
  `recipes(minutes) WHERE published`, a GIN index on `recipes USING gin(tags)` (the tag filter is a
  sequential scan today), and an index on `sessions(expires_at)` once a janitor exists.
- `ai_spend` is a four-way `UNION ALL` view summed under one global advisory lock on every reservation
  (`generation_budget.go:17` carries a note about it). A per-user daily rollup table, or at least an index
  on `created_at` for each source, will be needed before volume grows.
- `recipe_narrations.audio bytea` in Postgres: cheap to query across replicas, expensive to store and back
  up on Neon. R2 private prefix + key in the row keeps the cross-replica wait loop working
  (`narration.go:199-217`) with a `HEAD`.
- No `updated_at` on `users`, `collections`, `groceries`, `pantry`; no soft delete anywhere (account
  deletion is immediate, which is the documented policy, but uploaded R2 objects are never removed, see
  DEPLOYMENT.md).
- Two odd `// ponytail:` markers (`generation_budget.go:17`, `agent.go:134`) look like a private TODO
  convention; use `TODO(name):` so tooling and reviewers find them.

## Infrastructure and operations

- **No Content-Security-Policy** on the web app (`worker.ts:9-15` sets HSTS, nosniff, frame and
  permissions headers only). A report-only CSP first (`default-src 'self'; img-src 'self' https:
  data: blob:; media-src 'self' blob: https://media.savorly.cooking; connect-src 'self' wss:…`) would make
  any future XSS in rendered recipe text or model output far less valuable.
- **Capacity: the whole API is one `basic` container** (`wrangler.jsonc:30`: ¼ vCPU, 1 GiB) reached
  through one Durable Object. bcrypt cost 12 on ¼ vCPU is roughly a second per login, uploads are buffered
  fully in memory (`media.go:116`), touch-ups read up to 20 MB photos into memory, and narration buffers
  audio. `max_instances: 2` is never used because `getContainer(env.API)` is a singleton. Before launch:
  load-test registration and uploads on `basic`, or move to `standard`; consider argon2id with tuned
  parameters, and stream uploads to R2 instead of buffering.
- **Cold starts are visible**: after 30 idle minutes the first visitor waits up to 25 s behind a 503 retry
  loop (`worker.ts:21`, `api.ts:37`). It is handled gracefully, but a cheap cron ping (Worker `scheduled()`
  every 10 minutes during the day) or a shorter poll backoff (item 5 above) would keep the container warm
  without the DB cost.
- **Secrets hygiene is good** (`.env.*` ignored, secrets-file upload, no keys in git), but
  `scripts/deploy.sh` uploads every non-empty line of `.env.<target>` as a Worker secret, including the
  non-secret `ALLOWED_ORIGINS`/`APP_URL`; fine, just document that `wrangler secret delete` is the only
  way to remove one.
- **Backups and restore are not rehearsed** (PRODUCTION.md says "check the restore window"). Write the
  runbook: Neon PITR restore into a branch, point staging at it, verify, swap.
- **Analytics are absent**: no product events, no web analytics. Cloudflare Web Analytics (cookieless) is a
  one-line addition to `index.html`; a tiny `events` table or PostHog for feature usage would answer the
  questions the admin Overview cannot (what people search for, where onboarding drops).
- **Legal**: no privacy policy, terms, or Play's required account-deletion web page yet (tracked in
  PRODUCTION.md); the Worker can serve them as static assets.

## Web, SEO and performance

- **Code-split the bundle.** Everything ships in one file: the admin console, the recipe studio with
  WebRTC, camera, cropping, onboarding, Stripe plan settings. `React.lazy` with Metro's async imports on
  web for `Admin`, `RecipeStudio`, `Editor`, `Onboarding`, `PhotoCrop`/`RecipeCamera` would cut the first
  load for the common case (someone opening a shared recipe) by well over half.
- **No PWA manifest or icons** (`apps/mobile` has no `public/` directory): "Add to Home Screen" on phones
  produces a bookmark with no name/icon control. Add `public/manifest.json`, `robots.txt`, maskable icons,
  and `theme-color`.
- **Recipe photos are uploaded and served at camera resolution.** Profile photos go through
  `preparePhoto` (resized to 1024 px, `ProfilePhoto.tsx:127`) and the studio resizes before vision
  (`RecipeStudio.tsx:551`), but the editor's cover/gallery path (`Editor.tsx:139-160`) uploads the picked
  asset as is, so a 12-megapixel photo becomes a multi-megabyte JPEG that every feed card then downloads.
  Fixture Unsplash URLs are requested at `w=1200` everywhere and the server never derives thumbnails. Fix:
  `preparePhoto(uri, { max: 2048 })` in the editor, server-side or Cloudflare Image Resizing variants on
  `media.savorly.cooking` for cards, and `expo-image` (disk cache, blurhash placeholders, priority) instead
  of RN `Image` (`ui.tsx:535`).
- **Preconnect and font loading**: fonts are five TTFs loaded through JS (`App.tsx:945`), which delays
  first paint behind the splash. Preload them with `<link rel="preload">` on web, and preconnect to the
  media origin.
- **Four 401 console errors** for guests on every page load (the `/me` probe and private refreshes).
  Expected, but a `GET /session` that answers 200 `{signedIn:false}` keeps the console clean and avoids
  the retry logic treating auth as an error path.

## Mobile app

The shared `SheetHost` (one container that morphs between dialogs, drag-to-dismiss, Android back wiring,
keyboard lift, and the web `Modal`'s focus trap and Escape for free), the central reduce-motion handling,
the narration/voice lifecycle code and the idempotency of every paid call are all well done. Items 1 and 2
of the priorities (keep-awake and uploads) came from this layer too. The rest, each confirmed in code:

- **High — editor draft autosave collides and never restores edits.** The device-draft key is
  `savorly.draft.<user>.<id || 'new'>` (`Editor.tsx:101-102`). A sous-chef result opened in the editor has
  no id, so it autosaves under the same `…new` key as a hand-started recipe and overwrites that draft
  within 650 ms. Editing an existing recipe autosaves under `…<id>` but the restore effect bails whenever
  `initial` is set (`Editor.tsx:103-105`), so those drafts are dead writes while the screen promises
  "Drafts also save on this device as you type" (`Editor.tsx:722`). The debounced save is also dropped on
  unmount, losing the last keystrokes before navigating away. Fix: a per-session key for AI-seeded drafts,
  a "Restore unsaved changes?" prompt for edits, and a flush in the effect cleanup.
- **Medium — `FoodImage` and `Avatar` latch `failed` forever** (`ui.tsx:561,568`, no reset when `uri`
  changes). Typing a URL into "Or use an image URL" fails on every partial value, so the final valid URL
  shows the placeholder; the desktop gallery reuses one element across photos; before/after toggles in
  touch-up can stick. Track the failed URI, or `key={uri}`.
- **Medium — cancelling the share sheet on mobile web toasts the browser's `AbortError` text.**
  `Share.share` rejects on dismiss and `app.act` toasts every error (`RecipeDetail.tsx:221-227`,
  `store.tsx:112`), so a cancel shows "Share canceled" in English in every locale. Ignore `AbortError` and
  `dismissedAction`; the share text itself (`… minutes.`) is also untranslated.
- **Medium — the editor mounts a new video player per keystroke.** `r.video` is bound to the text field
  and `<VideoPlayer uri={r.video}>` mounts as soon as it is non-empty (`Editor.tsx:363,383-390`); expo-video
  keys the player on the source, so each character allocates a player that tries to load a partial URL.
  Keep typed text local and commit on blur; mount the preview only for a parseable http(s) URL.
- **Medium — the step-timer field cannot take fractional minutes.** The value is re-derived from
  `seconds` on every keystroke (`Editor.tsx:638-647`), so "1." renders back as "1" and "1,5" becomes 0.
  Use the existing `NumberField` (`ui.tsx:1644-1687`), which keeps unfinished input and accepts commas.
- **Medium — Android sheets have no modal semantics.** On Android the sheet is a plain absolute `View`
  (`ui.tsx:1146-1149`) and the only modal flag is the iOS-only `accessibilityViewIsModal` (`ui.tsx:1374`),
  so TalkBack can wander into the content behind it. Set `importantForAccessibility="no-hide-descendants"`
  on the app root while a sheet is open, as `App.tsx:420` already does for the recipe page.
- **Medium — several monochrome tokens fail WCAG contrast.** `soft` #A3A3A3 on white is 2.5:1 and is used
  for every placeholder, the update banner line and empty-slot icons; the unchecked `CheckRow` ring
  (`line` #D4D4D4) is 1.5:1; chip and secondary-button borders (`border` #E6E6E6 on #F4F4F4) are about
  1.1:1. Raise `soft` to at least #767676 where it carries text or icons and use ≥ #949494 for interactive
  outlines; `muted` and `onInk` pass.
- **Medium — plural forms are bypassed in 16 call sites.** The translator supports `count`-based
  `_one/_few/_many/_other` keys and `en.json` has them, but counts are interpolated as `{{v0}}` with one
  form (`Discover.tsx:338,796`, `Profile.tsx:131`, `Kitchen.tsx:278,770`, `RecipeStudio.tsx:837,1037`,
  `Onboarding.tsx:528`, `RecipeCard.tsx:179,237`, `SousChef.tsx:77`, `RecipeDetail.tsx:241,433,566,712`), so
  "1 recipes" and no correct Russian plurals; `ru.json:52` works around it with "Рецепты: {{v0}}". Other
  hard gaps: `'All saved'` rendered without `tr` (`RecipeDetail.tsx:601,624`), the raw
  'Reconnecting. Hold that thought…' caption (`RecipeStudio.tsx:466`), `tr(meal).toLowerCase()`
  (`Kitchen.tsx:729`, wrong for German nouns), an a11y label interpolating the ISO date
  (`Kitchen.tsx:285`), `placeholder="yourname"` (`Username.tsx:105`), `{job.error}` shown raw
  (`SousChef.tsx:280,466`), and the pantry "best before" free-text field that must be typed as
  `YYYY-MM-DD` and is compared lexicographically (`Kitchen.tsx:863-897`; needs a date picker).
- **Medium-low — every bookmark button subscribes to the whole store.** `useApp()` returns a new object
  on each provider render, so each `Save` inside every tile (`RecipeCard.tsx:24,81,188,250`) re-renders on
  any store change, defeating `memo(RecipeTile)` across hundreds of cards. Split a small library context
  (saved/following ids and toggles) the way `notifications.tsx` isolates toasts.
- **Medium-low — grocery check-offs are not optimistic and can race** (`Kitchen.tsx:680-690`): each tap
  awaits a PATCH then a full `GET /kitchen`; two quick taps issue overlapping refreshes that can arrive
  out of order and flip an item back. Reuse the store's `optimistic` pattern.
- **Low — accessibility details:** the hero card's label is "Let's get cooking" without the recipe title
  (`Discover.tsx:650-653`); 26 px icon buttons in the editor reach 38 px effective, under 44 pt
  (`Editor.tsx:311-331`); toasts rely on `accessibilityLiveRegion`, which iOS VoiceOver ignores
  (`ui.tsx:1729`, add `announceForAccessibility`); the sous-chef "thinking" loop ignores reduced motion
  (`SousChef.tsx:27-33`); fixed heights (search bar 52, pills 28/46, day cells 72) will clip at large
  Dynamic Type, prefer `minHeight` plus `maxFontSizeMultiplier`; `FoodImage` has no label, so the hero
  image is `alt=""` on the web (`RecipeDetail.tsx:866-873`).
- **Low — web history:** browser Back swaps the page under an open sheet instead of closing it first
  (`App.tsx:240-249`), unlike Android back and Escape.
- **Low — dead and duplicated code:** `color.ink2` and `s.divider` unused (`theme.ts:5,84`); two
  `requestKey` implementations (`utils.ts:16`, `RecipeStudio.tsx:65-73`); the Follow pill duplicated between
  `Discover.tsx:800-837` and `Onboarding.tsx:531-566`; one `busy` flag drives six unrelated buttons on the
  recipe page (`RecipeDetail.tsx:126,213-218`), so "Add to grocery list" spins Follow, Review, Plan and
  Report too; an unhandled rejection when leaving the sous-chef offline (`RecipeStudio.tsx:596`).

## Localization

The catalogs are in excellent shape: nine files with the same 770 keys, zero missing or extra keys,
zero placeholder mismatches, both plural groups complete in every language (including Russian
one/few/many/other), and the "untranslated" residue is vocabulary that is genuinely identical (`kcal`,
`Dessert`, `Video`). Register is consistent within each language (French `vous`, German `du`, Spanish
`tú`, Chinese `你`). Toasts, errors and section titles are translated at their display sites, so the
English constants in `store.tsx` and friends are not gaps. What is left:

- **Server messages are the real hole.** The API returns 150 distinct English error strings and only 15
  of them are catalog keys (the five password-auth messages, the handle rules, the operator notices).
  Of the 135 missing, about 100 reach normal users: every 429 ("Too many requests…", the three budget
  messages, the voice-time message), every provider 503 ("The sous-chef is not connected yet…"), the
  OAuth and reset-code errors ("That sign-in couldn't be verified…", "That reset code is invalid or
  expired…"), the whole of `models.go` validation, and the seven "Recipe not found." sites. Thirteen
  more are built with `fmt.Sprintf` or concatenation and can never match a key. Decide on one strategy:
  return stable error codes (`{"error": "…", "code": "recipe_not_found"}`) that the client maps to
  catalog keys, or add the ~100 user-facing strings to all nine catalogs and freeze their wording.
- **`job.error` is rendered raw** (`SousChef.tsx:280,466`, and rethrown through `photos.ts:96`), and none
  of its values (`jobs.go:136,215,277,283`, `studio_worker.go:63-69`) are catalog keys.
- **Seven AI prompt literals are untranslated**: the five "twists" (`RecipeDetail.tsx:70-74`), the
  nutrition prompt (`RecipeDetail.tsx:254`), the swap prompt (`RecipeDetail.tsx:343`) and "Create a recipe
  for …" (`Discover.tsx:381`). They become the user's own chat bubble in English and are sent to the
  model in English, so a French cook gets an English-flavoured answer.
- Display-site misses: the `'All saved'` pseudo-cookbook (`RecipeDetail.tsx:601,624`, also interpolated
  into "Saved to {{v0}}"), the "Reconnecting. Hold that thought…" caption (`RecipeStudio.tsx:466`), the
  share text's "minutes" (`RecipeDetail.tsx:226`), and the assistant's own interruption reply injected
  in English (`studio_worker.go:172`).
- **Terminology drift**: "pantry" is *garde-manger* in most French keys but *vos stocks* in three
  onboarding/sous-chef strings; Chinese alternates 食材库 / 储藏室 / 库存; Japanese 食材庫 / 食品ストック.
  A few labels read as calques: `Read it back` → ru "Прочитать обратно" (and ja/es drift to "re-read it
  yourself"), `Following` → de "Gefolgt", `Resume microphone` → de "Mikrofon fortsetzen", `Week` → ja
  "週間", `Failed` → es "Falló"; French profile stats mix genders ("Enregistrés" beside "Partagées").
- Dates and numbers follow the app locale everywhere outside the admin console (which hard-codes
  `Intl.RelativeTimeFormat('en')`). The week always starts on Monday (`utils.ts:4-15`), which is
  locale-blind for US, Japanese and Brazilian users, and device text-to-speech follows the UI locale even
  though step text is in the recipe's own language (`useCookingNarration.ts:31`).

## AI sous-chef subsystem

The design is strong where it matters: all 23 agent tools go through the app's own in-process router,
so the model cannot reach a route the app does not expose; every mutation carries the owner id; costs are
reserved before every provider call on all four paths; confirmation of consequential actions is enforced
by server-side sequencing under advisory locks; model output is stripped of media/published flags and
validated on every write. The issues below were each confirmed by reading the code.

- **High — `save_recipe_draft` silently unpublishes an adopted published recipe.** Once
  `generate_recipe_media` adopts one of the user's published recipes into the conversation, the build
  path forces `r.AIGenerated = true; r.Published = false` (`studio.go:512-513`) and `persistRecipe`
  updates the row, so "change the servings to 6" takes a live human recipe offline and relabels it as
  AI-generated, with no confirmation. Only `edit_recipe` has the `propose` gate (`agent.go:388-394`).
  `TestAssistantMakesMediaForAnExistingRecipe` drives this path and never asserts `Published`. Fix: when
  the draft is an adopted published recipe, refuse in favour of `edit_recipe` (or route through
  `propose`), and preserve `Published`/`AIGenerated` when `keep` is true.
- **High — a failed voice handshake keeps the full 30-minute reservation.** `voiceCreate` reserves up to
  1800 s (`voice.go:66-70`), and when the provider `Create` fails the `failed()` closure only sets
  `status='interrupted'` (`voice.go:83-85`), leaving `reserved_seconds=1800, finalized=false`.
  `usageOf` counts `reserved_seconds` for unfinalized sessions (`plans.go:124`), so with paid plans on, one
  failed attempt locks a Free member out of voice for 30 days and costs a Pro member 30 of 40 minutes and
  $1.50 of a $7.65 cap, with nothing billed by the provider. Fix: zero the reservation (`reserved_seconds=0,
  seconds=0, finalized=true`) on `Create` failure; finalize to a 15 s floor on `Attach` failure.
- **Medium-high — a failed turn leaves a stale pending confirmation alive.** The two lapses
  (`confirmed_revision=-1`, `pending=NULL`) run only when the turn succeeded (`studio.go:342-349`), so:
  turn N proposes "delete Lasagna", turn N+1 ("never mind, what's for dinner?") fails on a provider 5xx,
  and a "yes" to a dinner suggestion in turn N+2 can be taken as confirmation of the deletion
  (`confirm_action` only requires a user event after `pending_seq`, `agent.go:474`). Fix: perform both
  resets in the final settlement transaction regardless of the error.
- **Medium — settlement reuses the exhausted 3-minute context** (`studio.go:323,337,358-360`): after a
  deadline, `Begin(ctx)` fails, nothing is written, the action stays `running` until the 5-minute sweeper,
  and `studioMessage` answers 409 "still working" meanwhile. Settle with a fresh short context.
- **Medium — the studio worker processes every user's turn serially per replica**
  (`studio_worker.go:181-189` calls `processVoiceAction` synchronously inside the 1 s ticker): one slow
  turn (up to six model round trips) blocks every other conversation. Per-project exclusivity is already
  guaranteed by the claim predicate and the partial unique index, so a semaphore of ~8 goroutines (as
  `RunWorker` does with `slots`) is safe.
- **Medium — the whole history and every photo are re-sent on every turn.** `studio.go:261` loads all
  events with no window; every image in the conversation (up to 20 × 10 MB) is base64-attached to each of
  up to six rounds (`studio.go:303-311,330`, `ai/voice.go:54-58`). The reservation formula
  (`studio.go:171`) grows with it, so with paid plans three photos anywhere in a conversation reserve
  $0.61 per message against a Free cap of $0.50: every later message is refused with zero actual spend,
  and the app auto-resumes that conversation for six hours. Window the history, attach only recent images,
  downscale server-side in `studioImage`.
- **Medium — confirmation is sequence-based only.** In the follow-up turn the model may read third-party
  text (`get_recipe`, `get_reviews`) before calling `confirm_action`, and only the prompt stops injected
  text from reading as agreement. Defence in depth: accept `confirm_action`/`publish_draft` only as the
  first tool call of a turn, clear `pending` once any other tool runs, and show the pending description in
  the agent input.
- **Medium-low — `report_recipe` acts in the user's name without confirmation** (`agent.go:357-358`)
  while `review_recipe` goes through `propose`; injected text in a recipe can turn the assistant into a
  false-reporting vector against another cook. Gate it like reviews.
- **Medium-low — no sweep of stale voice sessions**: `heartbeat_at` staleness is only checked inside
  `voiceCreate` for the same user (`voice.go:44`), so a killed replica leaves sessions `active`, blocking
  `studioDelete` with 409 and inflating the admin's live-voice count. Add the sweep to the worker tick.
- **Low —** `generate_recipe_media` mutates the conversation (adopt, revision bump, approvals dropped)
  before the budget check and re-reserves on a repeat call (`agent.go:425-430`); three queries skip the
  suspended-author join (`agent.go:233,495`, `studio.go:40`); voice renewal at `maxSeconds-10` races the
  previous close and can get 409 (`connection.ts:160-165`, `voice.go:47-53`); no per-user cap on
  conversations or private source photos (20 × 10 MB each, `studio.go:50,189-215`).
- **Test gaps:** `voiceCreate` failure paths and their effect on `reserved_seconds`; nothing drives
  `monitorVoice` events (transcripts, delegations, usage updates, close paths); confirmation after a
  failed or timed-out turn; `save_recipe_draft` on an adopted published recipe; malformed tool
  arguments and mid-loop provider errors; long-conversation reservations versus `SpendCap`.

## Admin console

Authorization on `/admin` is sound: every route sits behind `requireAuth, requireAdmin`, every member
action goes through `manage()` (`admin_members.go:113-135`), sort/filter inputs are whitelist lookups,
every value is a bound parameter, and every write shares a transaction with its audit row. The gaps are
in what the rank rule does not cover and in how complimentary plans meet Stripe.

- **Medium — content actions ignore the rank rule.** `manage()` stops an appointed admin from touching
  an owner or a peer admin, but the recipe/review/job/voice handlers in `admin_content.go` (`recipeWrite`,
  `adminDeleteRecipe`, `adminDeleteReview`, `adminCancelJob`, `adminEndVoice`) load only title and author
  email and never check the author's rank (verified: no `manage`/`ownerSQL`/`adminSQL` call in the file).
  A compromised appointed-admin session can irreversibly delete every recipe and review of the owner.
  Fix: select `adminSQL`/`ownerSQL` for the author in those handlers and apply the same refusal, at least
  for delete and unpublish.
- **Medium — a late Stripe webhook can silently undo a complimentary plan.** `adminSetPlan`
  (`admin_members.go:371-384`) refuses only live Stripe members and leaves `stripe_subscription_id` in
  place, while `syncSubscription` (`billing.go:228`) applies non-live events whenever the stored id matches
  *or is empty*. A redelivered `customer.subscription.updated` for an ended subscription rewrites the
  comped row to `canceled`, dropping the member to Free with no audit entry. Fix: apply non-live events
  only on an exact id match and never over a comped row; clear `stripe_subscription_id` when comping.
- **Medium — the daily AI circuit breaker can be raised to $100,000 by any admin** (`admin.go:250-253`).
  Admins cannot appoint anyone, yet one request removes the only spend control. Make budget overrides
  owner-only, or cap them at a small multiple of the environment default.
- **Low — Restore is keyed to the audit log, not the row.** After an admin unpublish, the author can
  republish and unpublish again; the last audit action is still `recipe.unpublish`, so Restore
  (`admin_content.go:129-135`) now publishes the author's own draft. Record moderation state on the row
  (`unpublished_by_admin_at`). Note also that an author can undo a moderation unpublish in one tap.
- **Low — whole-object settings PUT without concurrency control** (`admin.go:266-282`, `Settings.tsx:54`):
  admin B saving an announcement from a stale form un-pauses the AI that admin A just paused. `FOR UPDATE`
  plus an `expectedUpdatedAt` check returning 409.
- **Low — an unverified owner can be suspended or deleted by an appointed admin.** In production
  `ownerSQL` requires `email_verified`, so until the owner has reset a password or connected Google,
  `manage()` sees an ordinary member. Treat any `ADMIN_EMAILS` address as owner-only to act on.
- **Low — comps inflate shared budgets and admins can comp themselves.** `memberBudgets`
  (`plans.go:64-78`) counts every non-free row as paying and prices an empty interval as monthly, so each
  complimentary plan adds free-tier headroom funded by revenue that does not exist; `adminSetPlan` uses
  `manage(c, true)` so self is allowed. Exclude `plan_interval=''` from headroom; forbid self-comps.
- **Low — `finishJob` has no status guard** (`jobs.go:238`): an in-flight video poll can flip an
  admin-cancelled job back to `completed`. Add `AND status IN ('running','processing')`.
- **Low — member deletion cancels Stripe and revokes Apple before the audited transaction**
  (`admin_members.go:405-426`), so a failed delete leaves side effects with no audit row; suspension leaves
  Stripe billing running for someone who cannot use the service.
- **Low — `member.edit` audits only field names** (`admin_members.go:200`), so a cleared handle or bio
  cannot be reviewed or restored; store before/after. The audit log also retains deleted members' email
  and name indefinitely, which needs a privacy decision.
- **Test gaps:** no test that an appointed admin is refused on an owner's recipe/review; appointed-admin
  coverage exists only for `suspend` and `admin`; no comp-then-webhook test; no `adminDeleteUser` →
  `cancelSubscription` test; no pagination or mass-assignment regression tests.

## Tests, CI and documentation

Coverage is better than the file count suggests: 64 Playwright tests (two against the real API and
SeaweedFS, the rest with mocked routes, including a fake WebRTC peer and a synthetic camera), 65 Go test
functions, and a 46-check HTTP integration script. Handles, OAuth, recovery, operator settings and the
SSRF address filter all have Go tests. The gaps are structural rather than per-feature.

### Tests

- **About 25 of the 65 Go tests silently skip locally.** `isolatedDB`
  (`database_integration_test.go:25-30`) is called at 22 sites across 10 files and skips without
  `TEST_DATABASE_URL`; the storage tests skip without `TEST_OBJECT_STORAGE`. Root `npm test` and
  `make check` set neither, so the admin, billing, studio, OAuth and narration suites never run on a
  developer machine (the app package finishes in 0.36 s without a database and 27.7 s with one). CI sets
  them. Fix: have `make check` default the URL to the compose database and fail loudly when unset.
- **Handler tests bypass the router and middleware.** Only four test files build the app with `New()`;
  the rest mount handlers on a bare `fiber.New()` (`studio_test.go:40-47`, `oauth_test.go:84-87`,
  `narration_test.go:73-76`, …). `requireAuth`, the auth limiter, per-route limits and the cookie/Origin
  rule (`app.go:92-115`) therefore have no Go test; CSRF is covered only by one line of
  `integration.py`. Fix: one table-driven router test hitting every private route unauthenticated (401)
  and with a cookie plus a bad Origin (403).
- **Native-only code has zero automated coverage** (Playwright is web-only and there is no Jest):
  `narration/player.ts`, `voice/transport.ts`, native `SocialButtons`/`auth/social.ts`, the StoreKit
  storefront gate, `updates.ts`, `welcome.ts`, SecureStore token handling, `PhotoCrop`, `RecipeCamera`.
  Add `jest-expo` with the iOS/Android presets for `src/lib/**` and the platform twins.
- **End-to-end never loads the production bundle.** CI builds `dist/` and then runs every browser test
  against `expo start --web` (Metro dev); the exported bundle Cloudflare serves is never opened. Serve
  `dist/` statically for at least the smoke and splash specs.
- **Flake risks:** fixed sleeps in `splash.spec.ts:48,62,68`, `performance.spec.ts:112,129,144`,
  `recipe-studio.spec.ts:343`; render regressions are `expect.soft`; `smoke.spec.ts` hard-codes seed
  content and `localhost:8333/savorly-media/`; `integration.py:73` asserts the default video model id
  and uses fixed past dates (lines 55-56); `accounts.spec.ts:3-15` mutates a shared fixture across tests;
  the local runner uses installed Chrome while CI uses Chromium.
- **Flows with no UI coverage anywhere:** signing in with an existing password, the reset-code dialog,
  sign-out, account deletion, editing or deleting an existing recipe, creating a cookbook, planner week
  navigation, pantry add/expiry, the review dialog, the report dialog, member/recipe/operations admin
  actions, offline retry. API-only gaps: `/auth/logout`, `GET /billing`, `/billing/portal`, delete paths
  for planner/pantry/groceries, `download()`'s redirect and DNS guard, `database.Seed`.

### CI/CD and repository hygiene

- `on: push` plus `pull_request` with no branch filter runs every PR commit twice; `verify` has no
  `concurrency` group and no `timeout-minutes`.
- No static analysis or vulnerability scanning beyond `go vet`: no `govulncheck`, golangci-lint, `npm
  audit` step, or Dependabot/Renovate (advisories are tracked by hand in VERIFICATION.md). Actions are
  pinned to major tags only.
- API and Metro logs go to `/tmp/savorly-*.log` and are not uploaded on failure; the readiness loop falls
  through silently after 120 s; Playwright browsers are reinstalled on every run.
- The Worker dry-run build is never run in `verify`, so wrangler or container config errors surface only
  on deploy. The deploy health wait is skipped when `PRODUCTION_URL`/`STAGING_URL` is unset, so
  `ship-android` can run with no health evidence. `--containers-rollout immediate` replaces all API
  containers at once, cutting live narration streams and voice sessions.
- The `ship-app.mjs` step relies on the Expo action exporting `EXPO_TOKEN` rather than passing it;
  `eas-version: latest` and `eas-cli@latest` are unpinned.
- **`apps/mobile/LICENSE` is Expo's own template ("Copyright (c) 2015-present 650 Industries")** left by
  create-expo-app and misstates the app's licensing; there is no root LICENSE, SECURITY.md, CODEOWNERS,
  CONTRIBUTING or PR template.
- The root `.dockerignore` is dead (both build contexts are `services/api`, which has its own); the
  Dockerfile has no `HEALTHCHECK`; the static binary could run from distroless.
- Release gating (environment reviewers, branch protection on `release`/`staging`) is not documented.

### Documentation drift

- `apps/mobile/AGENTS.md`, loaded as `CLAUDE.md`, is the stock Expo plugin template: it says "use Expo
  Router; routes live in `src/app/`" and assumes bun, neither true here (navigation is state in `App.tsx`,
  no `expo-router` dependency). It also omits what an AI assistant must know: `lint --max-warnings 0`, the
  i18n gate (`localization.spec.ts:81-159` fails when a `t()` literal is missing from any of the nine
  catalogs), `test:e2e` with `TEST_WEB_URL`/`TEST_API_URL`, the Go API, and `.web.tsx` twins. Rewrite it,
  or future AI-assisted changes will fight the codebase.
- README's project layout omits `internal/live`, `internal/narration`, `screens/admin`,
  `lib/{auth,i18n,narration,voice}`, `modules/storefront`, `tests`, and three of the four scripts.
- `docs/API.md` is missing `/auth/nonce`, `/auth/oauth`, the narration routes, all `/billing/*` and the
  eleven `/recipe-studio*` routes; `/billing/checkout` and `/billing/portal` are documented nowhere.
- `DEPLOYMENT.md` says "one instance" while `wrangler.jsonc` sets `max_instances: 2`;
  `TRUSTED_PROXY_HEADER` is set only in `wrangler.jsonc` and missing from every `.env*.example`, so a
  self-host behind another proxy silently loses per-visitor rate limits.

## Product gaps worth adding

Ordered by expected value for a cooking community, not by effort.

1. **Import a recipe from a link or a photo of a cookbook page.** The AI stack (vision agent, recipe
   JSON schema, draft flow) already exists; "paste a URL" is the single most common way people bring
   recipes into an app. Fetch through `download()` (SSRF-guarded), extract JSON-LD `Recipe` when present,
   fall back to the model, and save as a private draft with attribution.
2. **Metric/imperial and fraction display.** Units are free text (`Ingredient.unit`), so a US cook sees
   "200 g pasta" and a European cook sees "1 cup". A per-user preference plus a conversion table for the
   common units, and fractions (⅓, ½) in the scaled view.
3. **Step photos/short clips per instruction**, not only one cover video; the step model
   (`Step{title,text,seconds}`) has no media field.
4. **Comments on recipes** (beyond the one review per person), **"I cooked this" with a photo**, and
   **public cookbooks** (collections are private; sharing a cookbook is a strong growth loop).
5. **Weekly plan → one grocery list** (today groceries are added per recipe; a "shop this week" that
   merges and dedupes across the planner is the natural next step), and shared grocery lists per household.
6. **Push notifications**: new recipe from a cook you follow, pantry items expiring (README says
   "expiry reminders" but there is no notification, only a badge in the list), timer alerts (item 1).
7. **Print view** for the web (`@media print` with ingredients and steps only).
8. **Data export** (`GET /me/export` as JSON) alongside the existing account deletion, for GDPR access
   requests and for trust.
9. **Recipe versioning / forks**: "adapt" already creates a new draft; keep a `derived_from` link so
   adaptations credit the original and the original can show its variations.
10. **Offline cooking**: cache opened recipes (and the last narration) so a recipe keeps working in a
    kitchen with poor reception.
